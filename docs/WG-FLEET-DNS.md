# Автоматические DNS-записи WG Fleet

WG Fleet резервирует последовательные имена `wg1.pushok.shop`, `wg2.pushok.shop`
и далее. Запись реестра с номером сохраняется после архивирования; DNS worker
не перераспределяет номера. Один узел имеет один endpoint IPv4 либо IPv6,
соответственно запись A либо AAAA.

## Настройка на сервере Shop

Нужны переменные окружения процесса Shop:

- `WG_FLEET_DOMAIN` — основа имени; по умолчанию `pushok.shop`.
- `WG_FLEET_CLOUDFLARE_ZONE_ID` — идентификатор нужной зоны Cloudflare.
- `WG_FLEET_CLOUDFLARE_API_TOKEN` — API token с правом изменения DNS только этой
  зоны. Global API Key не используется. Токен не передаётся браузеру и Flow.

Токен задаётся защищённым механизмом окружения/секретов существующего
развёртывания. Его нельзя коммитить в репозиторий или помещать в публичную
команду. При отсутствии настроек внешние запросы не выполняются.

Worker создаёт только имя, точно соответствующее `wg<serial>.<WG_FLEET_DOMAIN>`
в реестре. Адресом может быть только публичный IPv4/IPv6; URL, порт вместе с IP,
loopback, private, link-local, multicast и специальные диапазоны отклоняются.
Профиль WGDashboard/API и UDP endpoint WireGuard остаются отдельными настройками.

## Что делает синхронизация

`app.wg_fleet_dns.sync(max_jobs=4)` выполняет ограниченную пачку операций вне
общей блокировки выдачи подписок. Для каждого узла сохраняются lease, попытки,
повтор, ID записи Cloudflare и случайная метка владения. Успешные записи повторно
проверяются раз в пять минут; ошибки получают возрастающую задержку повтора.

Созданные записи имеют `proxied=false` и `ttl=60`. Cloudflare proxy для обычных
HTTP-сайтов не должен включаться для WireGuard UDP endpoint. Состояние `ready`
появляется только после повторного чтения и совпадения записи с требуемыми
параметрами. Оно подтверждает конфигурацию у DNS-провайдера, **не прохождение
трафика и не завершение всех DNS-кэшей**. Допуск узла требует также успешного
внешнего WireGuard probe.

Если в Cloudflare уже есть запись с таким именем без сохранённой метки
владения, worker выставляет `conflict`. Совпадение IP не считается разрешением
изменить чужую запись. При потерянном ответе создания worker узнаёт собственную
запись по ранее сохранённой метке, подтверждает её ID и не создаёт дубликат.
Смена Cloudflare zone при существующем владении также требует отдельного
разрешения конфликта; старая запись не удаляется автоматически.

Изменение IP во время сетевой операции не позволяет старому результату
отметить новую настройку готовой: сохранение проверяет исходные domain,
endpoint IP и archived. Следующая попытка применит актуальную настройку.

## Удаление

DNS удаляется только для архивированного узла, у которого:

1. Все технические размещения имеют подтверждённое состояние `revoked`.
2. Нет подписок со статусом `active` или `pending`, привязанных к узлу.
3. Запись Cloudflare совпадает с сохранёнными ID, именем и меткой владения.

После DELETE worker подтверждает отсутствие записи повторным чтением.
Недоступный сервер с неподтверждённым отзывом пиров не проходит эту проверку.
Архивный номер и история владения сохраняются, даже когда DNS уже удалён.

Используются официальные методы Cloudflare
[Create DNS Record](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/)
и [List DNS Records](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/list/),
а также изменение и удаление по сохранённому ID. TLS проверяется; перенаправления
и прокси из окружения отключены. Тела ошибок провайдера и токен не сохраняются
в диагностике.

Тесты используют HTTP-ответы MockTransport. Они проверяют API-контракт,
владение, повтор после потерянного ответа и барьеры удаления, но не подтверждают
настройку Cloudflare в работающем развёртывании.
