# Автоподключения Pushok Flow: этап 1 — безопасная выдача существующего права доступа

Сервер Shop после обычного входа может обнаружить личную WireGuard-подписку и
отдать совместимый v1 JSON для установленного Flow. Этот этап **не создаёт**
новых заказов, peer, подписок или бесплатного периода при регистрации — это
требует отдельной политики прав и проверенной серверной интеграции.
Сессия MTProxy только для чтения профиля/баланса **не является** сессией Shop.

## API (только авторизованная сессия Shop)

- `GET /api/flow/wireguard/connections` — список только собственных WireGuard
  подписок и состояний, **без** конфигураций и личных ссылок.
- `GET /api/flow/wireguard/subscriptions/{sid}` — документ
  `pushok-flow-subscription` v1 для собственного существующего основного
  профиля. Статусы `active`, `expired`, `revoked`. На `pending` — 409.
  Ответ `no-store` и не содержит API-ключ WGDashboard.
- Ревизия хранится отдельно для каждой подписки и повышается при изменении
  конфигурации, срока или состояния. Повторный GET ревизию не увеличивает.
- Чужие профили — 404, анонимные запросы — 401. Неизвестное состояние не
  приводит к созданию или получению peer.

## Следующие блоки до автоматической выдачи при регистрации

1. Проверяемое одноразовое server-to-server связывание действующего пользователя
   MTProxy с Shop/будущим Pushok ID. Новое разрешение только для своего устройства,
   не административная сессия и не публичная ссылка на чужой профиль.
2. Политика начального доступа: включается владельцем явно, ограничения по времени,
   количеству устройств и глобальному бюджету, юридические условия, запрет дублей.
3. Транзакционный bootstrap с повторяемыми заданиями: существующий пользователь —
   при первом входе, новый — после регистрации. Успех только при подтверждённом peer.
4. Device-scoped короткоживущий обмен, зашифрованный URL подписки на устройстве,
   аудит отзыва. В Flow — после входа загрузка только собственного документа.
5. Сквозная приёмка на действующем WGDashboard: реальный handshake и трафик,
   продление, отзыв, восстановление после обрыва, повторная авторизация.

**Не считать данный этап полной автоматической регистрацией и подключением.**

## Device-scoped bearer link (основной профиль, пилот)

- `GET /api/flow/wireguard/subscriptions/{sid}/link` — после обычного входа Shop показывает состояние ссылки и версию.
- `PUT /api/flow/wireguard/subscriptions/{sid}/link` с `{"action":"enable|rotate|disable","version":N}` — серверная проверка владельца, активной подписки и версии.
- `GET /flow/wireguard/{token}` — без сессии браузера, только по случайному bearer-токену, возвращает v1 JSON. После ротации/отключения старый URL сразу отвечает 404; это **не** отзывает уже скачанный WG peer.
- Токен хранится только в зашифрованном виде и в виде хеша; ключ WGDashboard и пароль пользователя в нём отсутствуют.
- Это схема для основного профиля; **многоустройственная выдача с индивидуальным токеном каждого устройства — следующий этап**.
- Нельзя включать HTTP в продакшене, публиковать персональную ссылку или логировать URL вместе с токеном. При публикации через reverse proxy отключить access-лог для `/flow/wireguard/*`.

## Этап 2 — ограниченная автовыдача после входа Shop (код)

Добавлена отдельная политика `GET/PUT /api/admin/flow/wireguard/auto`
(только владелец, строгие поля `enabled`, `days` 1–30, `max_users` 1–100000,
`version` для конкурентного обновления). **По умолчанию выключено.**
Включение требует HTTPS, настроенных условий и активного WGDashboard с
`schedule_expiry=true` и `panel_timezone`, чтобы ранее скачанный конфиг
действительно перестал работать при истечении срока.

Shop после обычной регистрации, входа (email/Telegram/тикет), а также при
`GET /api/flow/wireguard/connections` запрашивает идемпотентную постановку
в очередь. **Сетевых запросов к WGDashboard при авторизации нет.**
Для одного Shop `user_id` выделяется максимум одна начальная WireGuard-подписка,
один постоянный идентификатор peer и одно резервирование квоты.
Существующие, в том числе платные и истёкшие, подписки WG не заменяются.
Квота учитывает ожидающие выдачи заявки, перезапуск и повторный вход.

Фоновый worker создаёт peer через существующий адаптер, подтверждает серверное
задание истечения, получает конфигурацию и только после этого отмечает доступ
активным. При сетевой ошибке повторяет тот же peer без сохранения ключей в
журналы. Выданные по политике профили помечаются как `trial` и имеют
ноль дополнительных устройств. Отмена политики не снимает уже выданный
доступ; серверное истечение продолжает действовать.

**Границы:** это Shop-пользователи. Пока нет проверяемого моста идентичности
MTProxy → Shop и scoped токена Flow, вход в MTProxy не может создавать/читать
Shop-подписки. Пользовательское автоматическое добавление в APK будет отдельным
этапом. Привязка к живой панели и завершение установки на VPS требуют проверки.
