## Критичные найденные и исправленные дефекты

1. Сценарий «ожидающий платный заказ + автоматическое бесплатное продление»: ранее сравнение с временным окном 60 секунд могло не учесть более старый заказ со статусом pending, что приводит к конфликту выдачи. Исправлено: проверка относится ко всему времени с исходной бесплатной активации. Добавлен регрессионный тест.
2. При обработке задач повторное бесплатное продление теперь сверяется с актуальным состоянием тарифа и наличием платных заказов. Это уменьшает риск выдачи льготного доступа после изменения владельцем коммерческой политики.
3. Ранее внедрённая функциональность бесплатных тарифов имеет тесты для одноразовой выдачи, лимита активаций, автопродления и перехода к платным условиям. Эти тесты **добавлены**, но результат их исполнения не подтверждён.

## Обзор основных систем

| Подсистема | Что обнаружено в коде | Что осталось подтвердить |
|---|---|---|
| Идентификация | PBKDF2-HMAC, constant-time сравнение, сессии в БД с SHA-256, HttpOnly/SameSite | эксплуатационная конфигурация HTTPS, CSRF во всех изменяющих обработчиках, восстановление аккаунтов |
| Telegram | проверка HMAC initData и времени | реальный Mini App и конфликт нескольких устройств |
| Платежи | YooKassa webhook используется лишь как триггер, результат сверяется по API, очередь повторов | реальные СБП/Stars, ошибки подтверждения, повторные webhook, возврат |
| Тарифы/промокоды | версии и снимки условий, бесплатные тарифы с политиками | выполнение полного набора тестов и миграций, пиковые параллельные заявки |
| Выдача | идемпотентные ключи и очередь paid→active, повтор после сбоев | реальный 3x-ui, WGDashboard, отключение при потере связи |
| Бесплатные лимиты | `free_traffic_gb` передаётся в 3x-ui и проверяется на чтении | поведение статистики и фактическая блокировка по квоте на реальном сервере |
| WGDashboard | чтение, создание peer и настройка expiry при поддерживаемом адаптере | срок действия без настройки schedule_expiry, QR и импорт на телефоне |
| Pushok Flow | персональный WireGuard feed, шифрование и управление токенами | сквозной запуск Shop → WGDashboard → Flow |
| Pushok ID/MTProxy | HMAC мост короткого действия, привязка по Telegram ID | развертывание, совпадение версий и верификация связки |
| Админка | ролевые возможности, редакторы тарифов, настройки политик | матрица доступов по всем endpoint, мобильный UX и браузерные тесты |
| Обновление/backup | ступенчатый процесс с резервной копией и откатом | реальное восстановление Shop на тестовом volume, проверка версии main vs release |
| Документация | отдельные планы и спецификации, часть документов всё ещё ссылается на v0.055 | синхронизация с текущими контрактами и фактически установленной версией |

## Запрет на неподтверждённые обещания

- Speed limit для бесплатных профилей пока **не реализован**.
- Трафик-квоты WireGuard/WGDashboard пока **не реализованы**.
- Квота трафика + автопродление запрещены до подтверждённого сброса 3x-ui статистики.
- Изменения HEAD не означают, что код уже установлен на VPS.
- Нельзя выпускать релиз с утверждением «все проверки прошли», пока не будут получены результаты CI именно для соответствующего SHA.

## Следующий обязательный gate

1. `python -m pytest -q`, `node --check app/static/app.js app/static/admin.js` (двумя вызовами), `node --test tests/test_*_ui.cjs`.
2. GitHub CI: tests, Docker staging, WireGuard staging, installer staging, browser screenshot tests — все на одном SHA.
3. Тестовая миграция с копии рабочей базы и проверка отката.
4. E2E: бесплатно (с квотой/без) → активен → истечение → продление → переход на платный, а также отказ/повтор/две конкурентные заявки.
5. Проверка настоящего WGDashboard и 3x-ui, затем отдельный тест Flow и платёжных провайдеров.
6. Только после этого — релиз и управляемое обновление VPS.
