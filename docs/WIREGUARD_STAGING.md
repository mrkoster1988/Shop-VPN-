# Проверка настоящего WireGuard в CI — v0.027

`wireguard-staging` входит в reusable CI, от которого зависит Release. Его результат
нужно проверять в Actions для конкретного коммита: локальные unit-тесты проверяют
защиты самого harness, но не подтверждают handshake или прохождение пакетов.

## Топология и ограничения доступа

- Производственный Dockerfile магазина, настоящий HTTP API, SQLite в отдельном томе,
  обычный worker и `PAYMENT_MODE=manual`. Telegram и внешние платёжные API выключены.
- Отдельный тестовый образ: текущий агент из `agent/main.py`, wireguard-tools,
  iproute2 и iptables. Команды `wg` и API агента не подменяются.
- Две Docker bridge-сети с `--internal`: транспортная (магазин, VPN-узел, клиент)
  и сеть приёмника (VPN-узел и отдельный HTTP-сервис). Порты на хост не публикуются.
- Клиент и VPN-узел получают только NET_ADMIN поверх `--cap-drop ALL`.
  Нет `--privileged`, host network, SYS_MODULE, Docker socket или host bind mounts.
  У магазина capabilities отсутствуют, корневая файловая система read-only.
- Сервер создаёт отдельный kernel-интерфейс `wg-pushok` внутри своего namespace.
  Forwarding/NAT применяются внутри него, правила firewall хоста не меняются сценарием.
- DNS/default-route интеграция wg-quick не выполняется: из скачанного конфига
  используются ключи, адрес, endpoint, AllowedIPs, keepalive и MTU; отдельный маршрут
  к тестовому приёмнику направляется через туннель. Публичный интернет не проверяется.

## Последовательность приёмки

1. Собрать образы, создать помеченные внутренние сети и тома. Запустить агент и
   подтвердить, что peer пока отсутствуют. Отдельный клиент без туннеля не должен
   иметь доступ к приёмнику: это отрицательный контроль обходного маршрута.
2. Через API магазина зарегистрировать синтетического покупателя, добавить выключенный
   WG-сервер, выполнить настоящий health-check, затем разрешить продажи.
3. Оформить pending-заказ. До ручного подтверждения peer отсутствует. Подтвердить
   заказ дважды, дождаться обычной очереди выдачи и проверить единственный peer.
4. Получить `.conf` через приватный download API, сравнить с config API, проверить
   отказ без сессии. Использовать этот конфиг на отдельном клиенте.
5. Проверить kernel handshake и ненулевые счётчики в обе стороны. HTTP-приёмник
   должен вернуть уникальный nonce и исходный IPv4 именно VPN-узла после NAT;
   маршрут клиента должен идти через `wg-client`.
6. Купить продление, подтвердить дважды: subscription UUID, ключ/IP/endpoint и
   единственный peer сохраняются, срок увеличивается ровно на оплаченные дни.
   Повторный трафик продолжает проходить.
7. Перезапустить контейнер магазина: сессия и расшифрованный конфиг сохраняются.
8. Установить срок **только синтетической подписки** в прошлом внутри тестовой базы.
   Это сокращение ожидания месяца; API отзыва и worker не подменяются/не вызываются
   вручную. Дождаться штатного worker, состояния expired и отсутствия peer в ядре.
   Download API должен вернуть 404, новое TCP-соединение через старый профиль — отказ.
9. Удалить только созданные сценарием ресурсы, проверив ID и собственную метку.
   Прежние контейнеры/тома/сети/образы не удаляются; prune не выполняется.
   Ошибка очистки делает весь результат неуспешным.

## Запуск и отчёт

Только одноразовый Linux runner с root, Docker и поддержкой kernel WireGuard.
Сценарий откажется без `--disposable`; неподдерживаемое ядро даёт ошибку, не skip.
В CI используется `ubuntu-latest`, тайм-аут задания — 15 минут.

```bash
sudo python3 tests/wireguard_staging.py --disposable \
  --source "$PWD" --report /tmp/shop-wireguard-staging.json
```

JSON создаётся с правами 0600 без перезаписи. Он содержит события, результат очистки
и границы проверок; конфиги, ключи, cookie, токены и логины в отчёт не включаются.
stdout/stderr subprocess не печатаются при ошибке, поскольку могут содержать секреты.
Метка последнего завершённого этапа помогает найти место отказа.

## Что остаётся открытым

Этот прогон подтверждает настоящий зашифрованный трафик ядра WireGuard и IPv4 NAT
в контролируемой среде. Он не подтверждает публичную IPv4/IPv6-связность, DNS,
физическое устройство клиента, VLESS/панели, боевые платежи/чеки/возвраты, Telegram,
публичный TLS/ACME, firewall провайдера, производительность или чистую установку VPS.
Отдельная приёмка по STAGING.md и INSTALL.md остаётся обязательной.
