# Инцидент: новый WGDashboard без пиров, Flow теряет интернет (24.11.2026)

## Наблюдения
- Новый веб-адрес панели, предоставленный пользователем: `http://193.238.155.39:10086`.
- На предоставленном изображении WGDashboard интерфейс `wg0` зелёный, количество клиентов `0 / 0`.
- На видеозаписи в Flow виден ранее сохранённый профиль `Pushok WireGuard` из подписки `Моё подключение Pushok`, но видеозапись не демонстрирует успешного handshake.
- Пользователь сообщает о потере доступа к интернету при включении туннеля; исключённые из туннеля приложения продолжают работать.
- Это не подтверждает точный корень потери трафика (нужно проверить handshake, UDP, маршруты, DNS и фактический Endpoint).

## Два важных ограничения текущего кода Shop
1. `app/servers.py` отклоняет внешний HTTP API URL: для публичного IP нужен **HTTPS**. Веб-панель по `:10086` нельзя прямо добавить как внешний HTTP API URL Shop; туннель/прокси между Shop и WGDashboard допустим только в частной защищённой сети с проверенными границами доверия.
2. Если к существующему серверу уже привязаны подписки, `servers.update` не разрешает изменить его `url/api/configuration`. Новый WGDashboard нужно завести как отдельную ноду, затем выполнить явную миграцию прав доступа и выдать/обновить конфиги. Нельзя просто менять сохранённый URL или считать старый ключ действующим на новой панели.

## Восстановление: безопасный порядок
1. Отключить Flow на телефоне, чтобы вернуть обычный интернет; оставить приложения с прямым трафиком без изменений.
2. На WGDashboard проверить `wg0`, реальный UDP ListenPort, Endpoint публичного WireGuard IP и статус forwarding/NAT; не публиковать private key, токены и конфиги.
3. Настроить API WGDashboard за **HTTPS** с доверенным сертификатом или через защищённое приватное соединение, не открывая порт панели всему интернету. Раздельно настроить firewall для API (TCP) и WireGuard (UDP).
4. В админке Shop создать новую ноду `wgdashboard`, конфигурация `wg0`, с API-токеном панели; сохранить **неактивной**, выполнить «Проверить», потом активировать. Проверять публичный `server.health`, `error_code` без секретов.
5. Для **нового тестового аккаунта** оформить отдельное подключение через Shop, дождаться `active`, проверить появление пира на `wg0` и `wg show wg0`. Не удалять существующие пиры вслепую.
6. Проверить прямым клиентом WireGuard с только что выданным конфигом: handshake и трафик, DNS и NAT. Если handshake нет — проверить Endpoint, UDP port, серверные ключи и firewall; если handshake есть без интернета — смотреть forwarding/NAT, MTU и DNS.
7. Только после проверки — синхронизация Shop → Flow, принудительное обновление подписки, проверка выбранного профиля и повторение теста. Старые профильные ключи не считать автоматически перенесёнными.
8. Для действующих клиентов запланировать миграцию с учётом сохранённых ID и отзыва старых профилей после подтверждения работоспособности новых.

## Правила
- Не копировать настройки с PrivateKey в GitHub issues, чаты или логи.
- Не создавать реальные подписки тестом без соответствующей явной тестовой учётной записи.
- Не сообщать об исправлении интернета до **наблюдаемого handshake и доступного интернета**.
- Публикация исходников сама по себе не обновляет VPS.

## Пример безопасной диагностики на сервере WGDashboard (без ключей)
```bash
sudo wg show wg0 interfaces
sudo wg show wg0 listen-port
sudo wg show wg0 peers | wc -w
sysctl net.ipv4.ip_forward
sudo ss -lun | grep -E ':51820[[:space:]]' || true
```
`wg show wg0 peers` выводит публичные ключи — в примере остаётся только количество; секреты не выводятся. UDP порт может отличаться от 51820.
