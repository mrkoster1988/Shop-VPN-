# Управление распределением серверов Shop

Кабинет /admin → «Серверы» и «Распределение». Разработчик настраивает адреса, секреты, лимиты и режимы панелей в существующем разделе. Новый раздел управляет порядком назначения и наблюдением.

## Распределение

- Учитываются активные узлы нужного протокола без ошибки API, с разрешёнными новыми назначениями и свободным слотом основной подписки. Pending-подписки занимают слот. Ёмкость 0 означает отсутствие заданного лимита.
- Основные узлы всегда раньше резервных. Резерв выбирается только при отсутствии подходящего основного узла и включённом резерве. Более высокий приоритет (0–1000) выбирается раньше в своей группе.
- При равном приоритете стратегия least_count выбирает меньше занятых подписок; utilization — меньшую долю заполнения конечного лимита. При utilization безлимитные узлы внутри одной группы идут после конечных, по числу занятых подписок. В конце — стабильный порядок created/id.
- При включении требования свежей проверки нужны health=ok и возраст от 0 до настроенного числа минут. Без требования сохраняется прежняя совместимость с health=unknown.
- Платная первая выдача, пробная выдача и стартовая WireGuard используют общий выбор. Для последней дополнительно требуется WGDashboard с настроенным серверным заданием окончания срока.
- Новые правила не меняют server_id, endpoint или приватные ключи уже привязанных подписок. Продление и повтор выдачи работают на прежнем узле по существующему контракту. Резерв не является автоматическим failover живого туннеля.
- Лимит считает основные подписки, не дополнительные peer, байты, скорость или CPU. Следующий узел на экране — рекомендация по текущему снимку, не резервирование.

## Мониторинг

Автомониторинг выключен по умолчанию. Настраиваются интервал 1–1440 минут и 1–4 последовательные проверки за цикл. Отдельная задача обрабатывает active/draining, не меняет профили и не отключает peer. Проверка API имеет таймаут 30 секунд, ошибка исключает узел из новых назначений; последующая успешная проверка восстанавливает его доступность для выбора. Политика и версия профиля проверяются при сохранении результата. Ручная проверка также пишет историю; сохраняется не более 100 записей на узел, экран показывает последние 20. В истории нет ответа API, URL панели и секретов. Длительность — время запроса к API, не сетевой RTT клиента и не скорость VPN.

## Контракт и права

GET /api/admin/server-routing и GET /api/admin/server-routing/history/{sid}: просмотр. PUT /api/admin/server-routing/policy: version и все поля политики. PUT /api/admin/server-routing/nodes/{sid}: version (правил узла), server_version (профиля), priority, reserve, accept_new. Разработчик может делегировать server_routing администратору только вместе с servers_read; индивидуальные права дополнительно ограничивают общий набор. Оператор панелей может читать новый отчёт, модератор не получает доступа. Эти права не дают новых возможностей изменения ключей. Диагностика использует те же критерии допуска.

Три новые таблицы создаются пустыми и входят в резервную копию. Восстановление требует проверить актуальные правила и состояние реальных панелей; не запускать параллельно два worker. Перед включением мониторинга/строгой свежести проверить API всех нужных узлов на стенде. Продуктовый CI не доказывает качество пользовательского трафика.
