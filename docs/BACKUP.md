# Резервные копии и восстановление — v0.021

Инструмент `scripts/backup.py` сохраняет **всю базу магазина и точный файл .env** в одном
зашифрованном `.pvb`-файле. Нужен отдельный пароль длиной от 16 символов. Это не
`ENCRYPTION_KEY`: ключ базы находится внутри защищённой копии. Без пароля архив не
восстановить. Храните пароль отдельно от копий и переносите проверенные копии за пределы
сервера. Копирование в удалённое хранилище, расписание и автоматическое удаление старых
копий пока не реализованы; существующие файлы инструмент не перезаписывает.

Архив содержит согласованный снимок SQLite через Backup API (включая зафиксированные
данные WAL), `.env` и манифест размеров/SHA-256. Весь контейнер архива защищён Fernet с
аутентификацией; ключ выведен из пароля PBKDF2-HMAC-SHA256, 600 000 итераций, случайная
16-байтовая соль. Пароль в командной строке не принимается и в отчёт не попадает.

Если часть настроек передана только через Compose/окружение и отсутствует в `.env`,
сохраните её отдельно: утилита не собирает все переменные процесса.

Секреты сервера, подписок, устройств, токенов ссылок и обеих очередей смены ключей
расшифровываются для проверки **без вывода значений**. Проверяются SQLite integrity_check
и foreign_key_check. Копия не создаётся при несовпадающем ключе; если ENCRYPTION_KEY задан
в окружении процесса, он также должен совпадать с `.env`. В базе без зашифрованных записей
возможна только проверка формата ключа и совпадения с окружением.

Ограничения первого формата: база до 128 MiB, `.env` до 1 MiB, архив до 180 MiB.
Копирование SQLite ограничено 30 секундами работы Backup API; при высокой нагрузке
повторите операцию. Требуется свободное место для временного открытого снимка и архива;
операции выполняются в памяти и приватном временном каталоге. Это инструмент для Linux,
Python 3.12 и зависимостей из `requirements.txt`.

## Обычная Python-установка

Запускайте из каталога проекта тем Python, где установлены зависимости:

```bash
mkdir -m 700 backups
python scripts/backup.py create --database data/shop.db --env .env --output backups/shop-v021.pvb
python scripts/backup.py verify backups/shop-v021.pvb
python scripts/backup.py restore backups/shop-v021.pvb --target /opt/pushok-recovered-v021
```

`create` запрашивает пароль дважды; `verify` и `restore` — один раз. Для запуска без
терминала используйте `--password-file /root/pushok-backup-password` (обычный файл с
правами 0600 или более строгими) либо `PUSHOK_BACKUP_PASSWORD` в окружении. Не сохраняйте
пароль архива в `.env` магазина. Не передавайте `.env`, пароль и открытые снимки в Git,
чат или журналы. Итоговый JSON содержит только результат, счётчики и время/релиз.

## Установка через Docker / установщик

Образ v0.021 включает `/app/scripts/backup.py`. Рабочий магазин можно не останавливать
для создания согласованного снимка SQLite. Не редактируйте `.env` во время операции.
Команды ниже предназначены для Bash на сервере, с доступом к Docker:

```bash
cd /opt/pushok-vpn
project=$(python3 -c 'import json; print(json.load(open("installer.json"))["project"])')
compose=(docker compose --project-name "$project" --env-file "$PWD/.env" -f "$PWD/compose.install.json")
mkdir -p -m 700 backups
chmod 700 backups
backup_name="pushok-$(date -u +%Y%m%dT%H%M%SZ).pvb"
read -r -s -p 'Отдельный пароль копии (от 16 символов): ' PUSHOK_BACKUP_PASSWORD
printf '\n'
export PUSHOK_BACKUP_PASSWORD
"${compose[@]}" exec -T -e PUSHOK_BACKUP_PASSWORD shop python scripts/backup.py create --env-stdin --output "/tmp/$backup_name" < .env
"${compose[@]}" exec -T -e PUSHOK_BACKUP_PASSWORD shop python scripts/backup.py verify "/tmp/$backup_name"
"${compose[@]}" cp "shop:/tmp/$backup_name" "backups/$backup_name"
chmod 600 "backups/$backup_name"
unset PUSHOK_BACKUP_PASSWORD
```

Выполняйте последующий шаг только после успешного предыдущего: JSON должен содержать
`ok: true`, код завершения — 0. Пароль можно очистить `unset PUSHOK_BACKUP_PASSWORD`
также при любой ошибке. В `/tmp` контейнера остаётся только зашифрованный архив; его
можно удалить после переноса и проверки внешней копии. При обычном `compose.yaml`
вместо чтения `installer.json` задайте массив
`compose=(docker compose --env-file "$PWD/.env" -f "$PWD/compose.yaml")`.

Docker-создание и перенос в этой среде не выполнялись: команды требуют приёмки на VPS.
Проверка архива после скачивания с удалённого хранилища обязательна: используйте `verify`
над **скачанным файлом** инструментом того же релиза. Сам по себе успешный `cp` этого
не подтверждает.

## Восстановление на другом сервере или после потери контейнера

1. Возьмите исходники **того же релиза, которым создан архив**. Первый формат намеренно
   отклоняет другую версию инструмента; код и Docker-образы в архив не входят.
2. Подготовьте Python 3.12 с зависимостями `requirements.txt` в отдельном venv. Это
   установка библиотек, запускать приложение/бота для проверки не требуется.
3. Скопируйте зашифрованный файл с внешнего хранилища и выполните `verify`. Затем
   `restore ... --target /новый/каталог` с этим же паролем. Родитель каталога должен
   существовать, сам каталог — **не существовать**, даже пустой. Перезаписи/`--force` нет.
4. Результат: `shop.db`, `.env`, `restore.json`, каталог 0700 и файлы 0600. Восстановлены
   тарифы, платежные состояния, очереди, серверные профили, устройства, trial, промокоды,
   реферальные привязки/баланс и приватные ссылки из снимка. Все браузерные sessions и
   одноразовые tickets очищены, поэтому нужно войти заново. ADMIN_TOKEN, VPN-ключи и
   приватные ссылки сохраняются; их автоматической смены нет.
5. До подключения восстановленной базы остановите единственный рабочий экземпляр
   магазина/бота. Подготовьте отдельный новый data volume, перенесите в него `shop.db`
   с владельцем uid/gid **10001:10001** и правами 0600; сохраните старый volume целиком.
   Не заменяйте `shop.db` поверх работающего SQLite и его старых `-wal`/`-shm` файлов.
   Подключите новый volume и восстановленный env_file к исходникам того же релиза.
6. Сначала проверяйте конфигурацию с `BACKGROUND_TASKS=false`: не запускайте второй
   polling-бот или worker параллельно первому. Проверьте вход, заказы, баланс, очередь,
   ключи и связь с реальными панелями. Диагностический скрипт `scripts/check.py`
   проверяет API, но не подтверждает работу VPN-трафика.
7. Отдельно согласуйте обработку платежей/очередей между временем снимка и аварией,
   затем включите ровно один worker/бот и проведите реальную приёмку. Автоматического
   reconciliation с состоянием узлов, возвратов или переноса новых оплат из потерянной
   базы нет. Возврат к более старому снимку не равен откату внешнего мира.

Инструмент восстанавливает проверенный **каталог данных**, но не переключает volumes,
не меняет существующий `.env`, не запускает Docker и не применяет обновления приложения.
Проверка архива не делает внешних API-запросов. Импорт настроек на другом домене и
проверку proxy/HTTPS выполняйте отдельно.

## Что сохранять отдельно

- Данные и настройки 3x-ui/Xray, WireGuard-агента, ключ WG_ENCRYPTION_KEY и состояние узлов.
- `installer.json`, Compose-файл, Nginx/Caddy, сертификаты и необходимые настройки ОС.
- Исходники/образ точного релиза и пароль резервной копии.

После аварии локального диска копия на том же VPS не поможет. Порядок и периодичность
выноса копий задаёт владелец. Проверку восстановления проводите на отдельном стенде по
`STAGING.md`; до неё нельзя считать полный процесс восстановления проверенным.
