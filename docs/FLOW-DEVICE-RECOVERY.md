# Pushok Flow: диагностика отказа Shop при получении конфига

## Почему «другой телефон» не всегда означает другой телефон

В Pushok Flow v0.60 Android преобразовывал **любой** HTTP 409 от
`/shop/api/flow/bridge/exchange` в `SHOP_DEVICE_BOUND`.
В Shop 409 также возникает при повторном MTProxy-билете и при несовпадении
идентичностей. Сообщение о чужом устройстве само по себе не доказывает
наличие другого телефона или WireGuard peer.

Новый контракт возвращает **код** в `detail.code`:

- `FLOW_DEVICE_BOUND` — сохранённая привязка другого client_id;
- `FLOW_PROOF_REPLAY` — одноразовый подписанный билет уже использован;
- `FLOW_IDENTITY_CONFLICT` — конфликт подтверждённой идентичности.

Никаких UUID, Telegram ID, приватных ссылок и токенов в ошибках нет. Новый
Android-клиент различает ошибки и поддерживает прежние точные строковые
сообщения Shop. Для неизвестного 409 он показывает нейтральный конфликт.

## Привязка первого телефона

Shop закрепляет client_id только после появления действительно выданной
активной WireGuard-подписки с сохранённым конфигом. `disabled` и `pending`
не резервируют устройство. Это предотвращает старую проблему: пользователь
попробовал вход до включения WGDashboard, получил `disabled`, но случайный
телефон уже навечно закрепился в базе.

## Инструмент разработчика (после развёртывания версии Shop с этим кодом)

`Пользователи → карточка пользователя → Проверить привязку Flow`.

Запрос `GET /shop/api/admin/users/{user_id}/flow/device` (developer-only)
возвращает только факт привязки, дату создания, наличие WG-подписки,
допустимость **безопасного** снятия и причину блокировки. Хеш client_id,
ключи WireGuard, личные ссылки и секреты не возвращаются.

Кнопка «Сбросить неиспользованную привязку» вызывает
`POST /shop/api/admin/users/{user_id}/flow/device/release` с подтверждением
и точной датой ранее прочитанной привязки. Действие под общим сервисным
замком и SQLite-транзакцией снимает **только** неиспользованный client_id.

Сброс **запрещён**, если уже выдавался или мог выдаваться WG-ключ. Для
`pending` он допустим только пока ни одна удалённая попытка не началась и
не сохранены секреты/credential_id. Не сбрасывать живую подписку ради
передачи прежнего private key другому телефону! Для этого нужен отдельный
подтверждённый процесс отзыва прежнего peer и выпуска нового ключа.

После разрешённого сброса открыть Flow на нужном телефоне и нажать
«Получить конфиг» повторно. Shop может ответить `disabled` или `pending`,
если выдача WG ещё не включена — сброс не создаёт peer и не продлевает срок.

## Что проверить до включения массовой выдачи

1. Раздел Shop «Flow · 30 дней»: политика включена, есть свободный лимит.
2. Рабочий WGDashboard на правильном узле, защищённый API (HTTPS или частный
   защищённый канал). Публичный административный HTTP с API-ключом запрещён.
3. «Пользователи → WireGuard → Проверить пир»: `no_subscription`,
   `key_not_created`, `peer_missing`, `peer_found` и причины ошибок.
4. Для неудачной новой выдачи — `pending` и безопасная функция «Повторить выдачу».
5. На Android реальный handshake, доступный интернет, split tunneling и отзыв.

**Важно:** коммит в GitHub сам по себе не обновляет VPS. Нужны успешный CI,
отдельный проверенный релиз Shop и развёртывание по штатному процессу.
Ни одна из этих функций не изменяет реальную базу или WGDashboard,
пока код не развёрнут.
