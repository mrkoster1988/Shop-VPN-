# Настоящий Docker-стенд в CI — v0.025

В reusable `.github/workflows/ci.yml` добавлен job `docker-staging`. Он входит и в
обычный CI, и в проверки перед автоматическим Release: успешные pytest/Node сами
по себе больше не достаточны для выпуска. Job сначала проверяет доступность настоящего
Docker daemon/Compose, затем выполняет `tests/docker_staging.py` от root на одноразовом
GitHub runner. Docker-команды не подменяются.

Здесь локально Docker недоступен. Результат реального прогона проверяется по job/logs
в GitHub Actions; текст этой инструкции описывает сценарий, а не заменяет его результат.

## Два независимых сценария

| Источник | Что выполняется |
|---|---|
| Обычная v0.021 | Подготовка текущего релиза → откат к v0.021 → повтор → активация |
| Managed v0.024 | Построение fixture v0.024 из v0.021 исправленным движком, откат/повтор; новые данные в действующем томе; переход к текущему релизу → откат → повтор → активация |

Исходники v0.021 и v0.024 берутся из фиксированных тегов **этого репозитория**, кандидат —
из проверяемого коммита. Начальная установка использует сгенерированные Compose/.env и
собранный образ, а не полный запуск apt/systemd-установщика. Для каждого сценария
создаются свой проект, временные тома, пароль копии и ключ шифрования.

В первом настоящем прогоне обнаружено, что Docker cp не видит созданный архив в
container tmpfs. В текущем контроллере передача исправлена на бинарный exec-поток.
Тег v0.024 не меняется. Промежуточный образ v0.024 строится из его настоящих исходников,
а fixture-операции создаёт движок кандидата с целевой меткой v0.024. Это подготовка
синтетического managed-layout, не утверждение об успешности прежнего контроллера v0.024.
Docker-команды и данные при этом настоящие; они не подменяются.

В базе есть только вымышленные пользователи и профили: заказы, оплаченный и пробный
доступ, дополнительные устройства, история смены ключей, приватная ссылка, промокод,
реферальное начисление/списание, sessions и tickets. Это прямое заполнение тестовых
данных; оно не доказывает успешное списание денег или выдачу на настоящем VPN-узле.
Фоновые задачи и Telegram выключены, адреса тестовых узлов не используются для API-запросов.

## Что подтверждает успешный job

- Docker build/run/exec и Compose up/stop работают с действительными named volumes.
- Логический хеш всех таблиц, кроме намеренно очищаемых sessions/tickets, совпадает
  после восстановления, обновления и отката. В managed-том добавляется отдельный
  маркер: выбор старой исходной базы вместо текущей обнаруживается.
- Восстановленная база принадлежит uid/gid 10001:10001, файл 0600, каталог 0700.
- В режиме ready API возвращает 503, health работает через настоящий локальный HTTPS.
  После активации старые sessions недействительны; новый HTTPS-вход и получение
  расшифрованного основного профиля через API проходят.
- В контейнере от обычного uid выполняются create/verify/restore копии. Восстановление
  в существующий каталог отклоняется. Данные остаются теми же, sessions очищаются.
- CLI status.py получает локальный отчёт текущей версии без внешних проверок.

HTTPS-прокси теста слушает только 127.0.0.1:443 и направляет запросы на случайный
локальный порт shop. Временный сертификат доверяется только тестовому Python-процессу
через SSL_CERT_FILE; системные сертификаты и hosts не меняются. Это не проверка ACME,
Caddy или подключения существующего Nginx на VPS.

## Запуск и очистка

**Не запускайте на боевом сервере.** Программа требует явного `--disposable` и root,
источники и Docker/Compose/OpenSSL. Команда job:

```bash
sudo python3 tests/docker_staging.py --disposable --baseline /path/to/v0.021 --intermediate /path/to/v0.024 --source /path/to/candidate --report /new/path/report.json
```

Проект получает уникальное имя. До работы фиксируются существующие Docker-ресурсы и
проверяется отсутствие коллизии. Очистка исключает прежние контейнеры/тома/теги и удаляет
только ресурсы собственного проекта/томов, созданные тестом; оставшиеся собственные тома
делают результат неуспешным. Docker prune, изменение production credentials и широкое
удаление volumes не используются. Код очистки отдельно покрыт локальными тестами.

Отчёт — только контрольные суммы, имена этапов и признаки выполнения, без данных
таблиц, .env, паролей и ключей. Ошибки команд проходят редактирование известных тестовых
секретов. JSON печатается в лог CI и сохраняется в новый файл с правами 0600.
Открытые снимки, архивы и исходники с env не публикуются как артефакты.

## Что остаётся отдельной приёмкой

Реальный VPS и его существующие сервисы, установка Docker через apt, systemd, свободное
место/нагрузка конкретного сервера, ACME/публичный DNS/Nginx/Caddy, настоящие панели и
VPN-трафик, реальные платежи/чеки, Telegram polling и действия worker на узлах.
Сценарии с этими составляющими остаются в STAGING.md. Сбой или отсутствие Docker-job
не считается прохождением приёмки.


С v0.027 в reusable CI добавлен отдельный обязательный `wireguard-staging` для
настоящего kernel handshake, контролируемого IPv4 NAT и автоматического отзыва
peer. Это отдельный сценарий из [WIREGUARD_STAGING.md](WIREGUARD_STAGING.md), а не
расширение заявлений о публичной сети/платежах/чистом VPS для данного upgrade-job.
