# Ручной учёт рекламных поступлений и возвратов — v0.033

Реализован журнал ручной сверки владельца. Магазин не выполняет списание или возврат,
не запрашивает банк и не проверяет подлинность введённого ID операции.
Владелец сначала проверяет фактическое движение денег во внешнем кабинете,
затем фиксирует результат. Это не платёжный документ и не расчёт прибыли.
Размещение спонсорского канала, доступность площадки и начало оплаченного срока
пока не управляются магазином. Кнопки оплаты и банковских реквизитов в кабинете нет.

## Порядок работы

1. Откройте одобренную заявку в разделе рекламы админки.
2. Для уже полученного внешнего платежа сверьте полную сумму из снимка заявки,
   укажите уникальный ID банковской операции и краткое основание проверки.
   Не вводите ФИО, номера карт, пароли или банковские реквизиты в ID/примечание.
3. Подтвердите флажком, что фактическое поступление проверено, и сохраните запись.
   Сервер отклонит другую сумму, неявное подтверждение, старую версию и повторный ID.
4. Для возврата сначала выполните и проверьте полный возврат во внешнем сервисе.
   Затем отдельно запишите его с собственным ID операции и основанием проверки.
   Кнопка «Сохранить» лишь записывает результат, деньги не перемещает.
5. После учтённого полного возврата рекламодатель может отменить заявку.

Статусы учёта: unpaid → confirmed → refunded. Во всех интерфейсах подтверждение
названо ручным учётом владельца. Длительность тарифа нигде не отсчитывается:
поступление не означает запуск спонсора. Модерация и журнал платежей независимы.
Смена цены в политике не меняет сумму старой заявки.

Поступление или возврат фиксируется только для одобренной заявки. Отмена с учтённым
поступлением блокируется до возврата. Проверка и запись выполняются в одной
транзакции: гонка отмены с поступлением не оставляет оплаченную отменённую заявку.
Частичные платежи/возвраты, повторная оплата после возврата и редактирование записей
не поддерживаются. Для нового размещения после возврата/отмены создаётся новая заявка.

## API и идемпотентность

Пути относительны PUBLIC_URL конкретной установки, в том числе с /shop.
Все перечисленные маршруты требуют ADMIN_TOKEN и общей проверки Origin.

| Метод и путь | Назначение |
| --- | --- |
| POST /api/admin/ads/requests/{id}/payments/receipt | Учесть проверенное поступление |
| POST /api/admin/ads/requests/{id}/payments/refund | Учесть проверенный полный возврат |
| GET /api/admin/ads/requests/{id}/payments | Прочитать журнал заявки |

Тело POST: operation_id (UUID), request_version, payment_version, amount (целые рубли),
reference (ID операции), note (основание), checked=true.
Версия учёта: 0 до поступления, 1 после него, 2 после возврата.
Возвращаются status, version, received_amount, refunded_amount, currency=RUB и entries.
ID операции нормализуется в нижний регистр, допускает 3–120 ASCII-символов:
буквы/цифры, двоеточие, точку, подчёркивание, дефис и слеш. Он уникален для всего
рекламного журнала установки, включая поступления и возвраты.

Повтор идентичного POST с тем же operation_id не создаёт записи или события повторно,
даже если заявка затем получила возврат/отменена. Ответ отражает текущий статус учёта.
Повтор UUID с другими данными/заявкой/действием — 409. Новая операция со старой версией,
повторным банковским ID или неверной суммой — 409. Некорректный ввод — безопасный 422.
Неизвестная заявка — 404. После потери ответа повторите исходный запрос с тем же UUID.

Рекламодатель получает только payment: status, version, received_amount,
refunded_amount, currency в своих заявках. ID банковских операций, основания,
UUID сохранения и внутренние записи ему не выдаются. Административный список
дополнительно содержит историю entries. Общий ADMIN_TOKEN не различает сотрудников;
события фиксируются как admin, именованные роли ещё не реализованы.

## Данные и проверка

ads_payment_entries хранит неизменяемые записи с уникальными operation_id/reference,
типом receipt/refund, суммой, основанием, отпечатком запроса и временем записи.
Для каждой заявки разрешены одно поступление и один возврат. События payment_receipt
и payment_refund добавляются в ads_events в той же транзакции.
Рекламный журнал не создаёт VPN-заказы, подписки и выручку в VPN-статистике.
Учтённые суммы не называются чистой прибылью: расходы, комиссии и финансовые отчёты
пока не реализованы. Суммы в этом журнале отражают утверждение владельца о сверке.

Повторная миграция не меняет записи. Журнал включён в зашифрованное резервное
копирование и восстановление; сессии после восстановления удаляются.
Для сравнения данных со старой схемой только новая пустая таблица исключается
из хеша; её наличие проверяется отдельно. Непустой журнал всегда участвует в хеше.
Docker-стенд использует синтетические операции, локальный HTTPS и настоящий архив,
но не делает банковских запросов, списаний, возвратов или показов в Telegram.

Следующий этап — реестр проверенных площадок и ручное подтверждение фактического
начала/окончания размещения с защитой от пересечений и учётом простоя.
