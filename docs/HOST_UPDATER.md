# Обновление из панели владельца

Служба работает отдельно на VPS и переживает остановку магазина. Веб-процесс не получает Docker socket или shell. Владелец сначала готовит план, затем подтверждает установку. Проверка релиза в 21:00 сама ничего не устанавливает.

## Десять выполненных частей этапа

1. Разделены проверка новых релизов и установка; ручная инструкция доступна без службы.
2. Источник ограничен стабильными релизами `mrkoster1988/Shop-VPN-`; тег разрешается в commit SHA, архив скачивается по этому SHA.
3. План проверяет совместимость существующим `upgrade.py`, содержит версии/коммит и действует 15 минут.
4. Перед остановкой под общей блокировкой повторно сверяются `.env`, Compose и метаданные установки.
5. Отдельная служба systemd слушает только `127.0.0.1` и принимает ограниченные команды с отдельным токеном.
6. SQLite-журнал вне БД магазина обеспечивает одну операцию и идемпотентность запросов по UUID.
7. Установка использует зашифрованную копию, проверку восстановления, отдельный том и сохранённый старый образ существующего обновлятора.
8. После явного подтверждения владельца служба выполняет подготовку и активацию. Откат допустим только до начала активации.
9. Панель показывает план, подтверждение, фазы и результат; потеря HTTP-ответа не вызывает повторную установку.
10. Добавлены контрактные, API/UI, браузерные и Docker/systemd сценарии; границы проверки перечислены ниже.

## Однократное включение на VPS

Нужна установка официальным мастером, Ubuntu 24.04, systemd и работающий Docker Compose. Произвольная конфигурация, незавершённое обновление или изменённые привязки не обходятся автоматически. Этот код пока находится в `Unreleased`; установленный v0.055 не содержит службы. Команды выполняются из полного каталога релиза, в который войдёт этот этап.

```bash
sudo python3 scripts/setup_host_updater.py --dir /opt/pushok-vpn --plan
sudo python3 scripts/setup_host_updater.py --dir /opt/pushok-vpn
```

Порт по умолчанию 9079, можно выбрать свободный `--port`. Настройка создаёт отдельный токен, пароль копии, файлы службы и добавляет `PUSHOK_HOST_UPDATER_PORT` / `PUSHOK_HOST_UPDATER_TOKEN` в `.env`. Затем пересоздаёт только shop, чтобы он прочитал настройки. Произойдёт краткий перерыв. Повторный запуск не заменяет ключи. Не добавляйте этот порт в публичный reverse proxy или firewall.

`/opt/pushok-vpn/updater/backup-password` (0600) нужен для восстановления зашифрованных копий; сохраните его во внешнем защищённом месте вместе с внешними копиями. Это не пароль панели. Не отправляйте файл или `.env` в чат. Исходный `.env` перед настройкой сохраняется в `updater/env.before`; при частичном сбое сначала проверьте состояние службы и конфигурации, не удаляйте журнал.

Служба `pushok-updater-<project>.service` устанавливается root. Исходники службы и конфигурация лежат в `<установка>/updater`, журнал и загруженные релизы — в `/var/lib/pushok-updater/<project>`. Служба не обновляет сама свой код; после будущего изменения протокола управления понадобится отдельное обновление службы. Не применяйте `Docker prune` и не удаляйте эти каталоги во время незавершённой операции.

## Сценарий владельца

1. В «Обновлениях магазина» проверьте релиз и откройте «Обновить».
2. Нажмите «Подготовить план». Магазин продолжает работать. Источник скачивается с фиксированных HTTPS-адресов без прокси/редиректов; архив ограничен 32 МиБ, распаковка — 64 МиБ и 2000 элементов. Ссылки, специальные файлы и выход из каталога запрещены.
3. Проверьте текущую/целевую версию и коммит. Сохраните внешнюю копию. Отметьте согласие на остановку, локальное копирование и активацию; нажмите «Установить обновление».
4. Пока служба строит образ, магазин работает. Затем он останавливается для копирования/миграции. Интерфейс может показать потерю связи; не запускайте новую операцию. Служба продолжает независимо от страницы.
5. После запуска магазина обновите страницу и при необходимости войдите заново. Ход и результат хранятся вне восстанавливаемой БД.

Один план используется для установки только один раз. Устаревший план либо изменение настроек требуют нового плана. Проверяется протокол службы `host_updater_protocol=1`; старые целевые релизы, не поддерживающие его, автоматически не применяются. Неудачный план не останавливает магазин.

## Прерывание и откат

После рестарта службы задания `queued`/`running` переходят в `interrupted`. Автоматического продолжения или повторной активации нет. Проверьте журнал и реальный магазин:

```bash
sudo python3 /opt/pushok-vpn/updater/host_updater.py status --dir /opt/pushok-vpn
```

До активации, для последней известной попытки, можно запросить возврат прежней версии:

```bash
sudo python3 /opt/pushok-vpn/updater/host_updater.py rollback --dir /opt/pushok-vpn
```

Команда обращается к работающей локальной службе и возвращает принятый запрос; окончательный результат смотрите через `status`. После начала `activate` откат базы запрещён, даже при ошибке health: могли поступить новые платежи или измениться VPN-узлы. Нужна ручная сверка по [UPGRADE.md](UPGRADE.md). Не обнуляйте журнал ради повторного запуска.

## API и проверки

Только владелец магазина: `POST /api/admin/updates/plan`, `POST /api/admin/updates/apply`, `GET /api/admin/updates/operation`. Для `/shop` добавляется этот префикс. Токен службы остаётся на сервере; обычные сотрудники не вызывают её API. Журнал админки фиксирует запросы, а журнал службы — результат пережившей перезапуск операции.

`test_host_updater.py`, `test_update_install.py`, `test_upgrade.py` и UI-тесты проверяют дубли, просроченный/изменённый план, рестарт, ограничения доступа и отката. Браузерный CI проверяет подтверждение и ход операции на мобильном экране. Docker-стенд выполняет HTTP → журнал → subprocess → настоящий Docker, копирование и активацию для обычной и ранее обновлённой установки. Стенд установщика отдельно проверяет службу systemd, связь из контейнера и рестарт.

Скачивание GitHub проверяется на контролируемых ответах; Docker-стенд использует checkout CI. Это не подтверждение установки будущего опубликованного релиза, реального VPS пользователя, внешнего бэкапа или живых платежей/VPN. Публикация установочного релиза и пробная установка остаются отдельными этапами.
