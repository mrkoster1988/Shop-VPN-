# SOO Pushok — P0: контракт Shop → Pushok Flow (WireGuard)

Статус: **контракт и тесты в разработке; публичная выдача ещё не подключена**.
Принят по межпроектному плану от 23.11.2026. MTProxy не затрагивается.

## Распределение ответственности

- **Shop** проверяет покупку, владельца, срок, устройство; создаёт/удаляет peer через закрытый WGDashboard API; хранит ключи зашифрованно и выдаёт индивидуальный HTTPS URL устройства.
- **Flow** загружает документ только по безопасному HTTPS, строго разбирает WireGuard, обновляет каталог атомарно; само подключение остаётся явным действием пользователя.
- **WGDashboard** управляет реальным WireGuard peer; отзыв URL не равен отзыву peer.
- **Pushok ID** и `@pushok_app` будут интегрированы позднее без повторной регистрации существующих пользователей.

## Формат P0

```json
{
  "schema": "pushok-flow-subscription",
  "version": 1,
  "revision": 12,
  "state": "active",
  "expires_at": 1893456000,
  "profiles": [
    {
      "id": "stable-device-a-peer-id",
      "name": "Pushok WireGuard",
      "protocol": "wireguard",
      "config": "[Interface]\\nPrivateKey = EXAMPLE_NOT_REAL\\nAddress = 10.0.0.2/32\\n"
    }
  ]
}
```

Значение `config` в этом примере исключительно демонстрационное; тесты не содержат настоящих ключей. Схема строго фиксирована, неизвестные поля запрещены. `revision` — целое число >= 1, монотонно растёт для **конкретной ссылки устройства**, включая изменение срока, состояния, имени и любого профиля. `expires_at` — Unix seconds UTC. Для `active` требуется 1–20 профилей; для `expired` и `revoked` всегда `profiles: []`. В P0 протокол только `wireguard`.

`id` профиля не меняется при обычном продлении, `name` не участвует в идентичности. Отдельные устройства не используют общий WireGuard приватный ключ или один токен доступа.

## Приём и обновление

- Если входящая ревизия **меньше** сохранённой — отклонить как устаревшую.
- Та же ревизия и идентичные данные — идемпотентный повтор.
- Та же ревизия, но иные данные — конфликт; нельзя подменять каталог.
- Большая ревизия — применить целиком после полной проверки.
- Невалидный JSON, TLS/сетевая ошибка, тайм-аут и 5xx **не** означают `revoked` и не стирают последнюю корректную копию.
- Подтверждённые `expired` и `revoked` выключают новые подключения. Отозвать реальный доступ необходимо на самом WG сервере.
- Запрещено помещать токен персональной ссылки, полный URL, конфигурацию, приватный ключ или ключ админ-API в логи, аналитику и диагностические отчёты.

## Работа до полного P1/P2

Файл `app/flow_subscription_contract.py` содержит чистые функции проверки и сравнения ревизий. Он **не** создаёт публичные ссылки, не связывает документы с покупкой и не меняет действующий `/sub/{token}` VLESS. Текущие `subscription_links` рассчитаны на основную VLESS-подписку, поэтому для WG нужны самостоятельные токены и версии **по устройствам**, без повторного использования таблицы VLESS.

Следующие обязательные задачи для Shop:

1. Таблица device-level Flow links: HMAC/хеш токена, зашифрованный секрет, разрешённое устройство, признак enabled, revision и атомарная ротация.
2. Авторизованный endpoint управления ссылкой для владельца устройства и отдельный публичный read-only endpoint с `Cache-Control: no-store`, без раскрытия админ-API.
3. Публиковать `active` только после подтверждённой выдачи peer. Истечение и отзыв должны соответствовать состоянию серверного peer; при ошибке отзыва сохранять видимую очередь повторов.
4. Инкрементировать revision в транзакции вместе с изменением опубликованного состояния, учитывать продление, изменение конфигурации и восстановление БД.
5. Общие положительные/отрицательные фикстуры с Flow, затем интеграционные испытания с настоящим WGDashboard: новое устройство, повтор, продление, отзыв, восстановление, трафик и DNS.

Проверка кода: `python -m unittest tests/test_flow_subscription_contract.py` или `python -m pytest -q tests/test_flow_subscription_contract.py`. Наличие тестов не означает, что они прошли CI или что VPN работает на сервере.
