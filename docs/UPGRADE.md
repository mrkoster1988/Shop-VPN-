# Управляемое обновление — v0.022

Первый поддерживаемый переход: **установка v0.021 через установщик → v0.022**.
Для более старых версий, изменённого Compose, внешних data volumes и повторного перехода
v0.022 → следующая версия нужен отдельный план. Скрипт останавливается до изменений,
если не узнаёт исходную конфигурацию. Это не универсальная миграция любого развёртывания.

Обновление готовится в новый named volume. Старый том и старый image ID сохраняются;
прокси, VPN-панели, устройства на узлах и другие контейнеры не обновляются. Во время
подготовки есть перерыв работы магазина. Сборка нового образа выполняется до остановки,
затем останавливается только shop. Пригласительные балансы, платежи, очереди и ключи
переносятся из согласованного снимка после остановки старого процесса.

## Команды

Пользуйтесь скриптом фиксированного релиза:

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.022/install.sh | bash -s -- --upgrade plan --dir /opt/pushok-vpn
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.022/install.sh | bash -s -- --upgrade prepare --dir /opt/pushok-vpn
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.022/install.sh | bash -s -- --upgrade status --dir /opt/pushok-vpn
```

Либо из полного каталога исходников v0.022:

```bash
python3 scripts/upgrade.py plan --dir /opt/pushok-vpn
sudo python3 scripts/upgrade.py prepare --dir /opt/pushok-vpn
sudo python3 scripts/upgrade.py status --dir /opt/pushok-vpn
```

`plan` не меняет установку и не вызывает Docker. `prepare` требует root, доступный Docker,
один работающий контейнер shop, свободное место для исходников/образа/нового тома и копии,
а также успешную локальную и публичную проверку `/shop/health`. Отдельный пароль архива
запрашивается через терминал дважды, минимум 16 символов. Можно передать
`--password-file /root/pushok-backup-password` с правами 0600. Для запуска от root также
поддержан `PUSHOK_BACKUP_PASSWORD`; пароль не передаётся аргументом Docker и не пишется
в журнал. Для sudo используйте файл либо диалог, не рассчитывайте на сохранение окружения.

Перед подготовкой сохраните независимо базу/.env, настройки инфраструктуры и внешнюю
копию по [BACKUP.md](BACKUP.md). Не редактируйте `.env`, Compose и installer.json во время
операции; контрольные суммы блокируют действия при посторонних изменениях. Для установщика
и обновления используется общий неблокирующий файловый lock.

## Что делает prepare

1. Проверяет версию/структуру установки и исходников, создаёт приватный каталог
   `upgrades/<operation>/`, сохраняет метаданные и собирает отдельный образ.
2. Останавливает старый shop. Вспомогательный контейнер без сети получает старый том
   только для чтения. После остановки он переносит shop.db и возможный WAL в приватный
   writable staging; затем Backup API старого инструмента создаёт логический снимок.
   Это обход ограничения read-only WAL, а не сырое копирование работающей базы.
3. Создаёт зашифрованную копию базы/.env старым образом. Сохраняет `backup.pvb` на хосте
   с правами 0600, читает обратно именно этот файл и проверяет его. Старый ключ не меняется.
4. Восстанавливает снимок в `/app/data/restored` нового тома. Сессии/tickets очищаются,
   остальные записи и приватные ссылки сохраняются. Новым образом без сети запускаются
   только init_db и проверка расшифровки — без worker, бота и обращения к панелям.
5. Переключает только shop на новый image/volume с `MAINTENANCE_MODE=true` и
   `BACKGROUND_TASKS=false`. Проверяет запуск, локальный и публичный health. В journal
   появляется `phase: ready`. Старые данные не удаляются и не используются новой версией.

Лимиты первого перехода: база до 128 MiB, база вместе с WAL до 256 MiB; временный том
помощника — 768 MiB, плюс память для шифрования и место на диске. При превышении операция
останавливается и пытается вернуть прежний магазин. Не запускайте другие экземпляры,
которые пишут в тот же том или опрашивают того же бота.

В `ready` магазин показывает страницу обслуживания, все покупки/вход/приватные маршруты
возвращают 503 с Retry-After. Доступен только `/health`. Обработчики фоновых задач не
стартуют даже при ошибочно включённом BACKGROUND_TASKS. Перерыв продолжается до
`activate` либо `rollback`; подготовка сама магазин для покупателей не открывает.

## Активация и откат

После проверки журнала, копии и доступности health включите новую версию:

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.022/install.sh | bash -s -- --upgrade activate --dir /opt/pushok-vpn
```

`activate` восстанавливает исходные настройки BACKGROUND_TASKS/MAINTENANCE_MODE из Compose
и `.env` и пересоздаёт только shop. При обычных настройках магазин открывается и один
worker/бот продолжает очередь. Если фоновые задачи были явно выключены до обновления,
они не включаются насильно. После успешной проверки состояние — `committed`.

**До начала активации** можно вернуться к старому образу и нетронутому тому:

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.022/install.sh | bash -s -- --upgrade rollback --dir /opt/pushok-vpn
```

Скрипт останавливает новый shop, возвращает прежние метаданные и старый immutable image ID,
запускает старый том и проверяет health. Исходники root/source и `.env` не заменяются.
Состояние — `rolled_back`; повтор rollback не перезапускает магазин второй раз.

Если prepare падает до активации, выполняется попытка такого же отката. При её отказе
журнал получает `recovery_required`; после устранения причины выполните `status`, затем
`rollback`. При прерывании/перезагрузке журнал сохраняет намерение и последнюю фазу;
автоматического продолжения после старта ОС нет. Не удаляйте его ради повторного prepare.

**С начала activate автоматический откат базы запрещён**, в том числе при
`activation_failed` или зависшем `activating`. Новые worker/бот/API могли уже изменить
платежи, баланс или состояние узлов. Сначала остановите поступление изменений и сверяйте
события с момента снимка по процедуре аварийного восстановления. Нельзя вернуть старую
базу как обычный откат кода после новых продаж. Повтор committed-активации — без действий.

## Что остаётся после обновления

- `upgrade.json`: идентификатор операции, фаза, версии, контрольные суммы и привязки
  ресурсов; без `.env`, пароля архива и ответов провайдеров. `status` выводит только
  идентификатор, фазу, версии, флаг начала активации и этап последней ошибки без её текста.
- `upgrades/<operation>/`: source нового релиза, исходные installer/Compose-метаданные
  и зашифрованная копия. Каталог 0700, приватные файлы 0600. Перенесите архив за пределы VPS.
- Старый volume и образ, новый volume и образ. Автоматического удаления нет.
- `installer.json` указывает managed_upgrade. Повторный install.py отказывается
  пересобирать магазин из старого root/source. Для статуса/активации/отката используйте
  upgrade.py, а не обычный повтор установки.

Новая утилита backup v0.022 читает совместимые архивы v0.021 и v0.022. Копия для отката
этого перехода создаётся **старым** образом v0.021; сохраняйте его и исходники до приёмки.
Смена домена/порта/прокси не входит в обновление. Изменённые установки нужно сначала
разобрать отдельно; обходных флагов для отключения проверок нет.

Docker build/run, миграция через реальный volume, сетевые health и полный сценарий на VPS
в текущей среде не запускались. Проверки координатора подменяют Docker; отдельно тестируются
реальный SQLite/WAL и шифрование. До production необходима приёмка по STAGING.md.
