# Управляемое обновление — v0.048

Поддержаны переходы **v0.021 / v0.022 / v0.023 / v0.024 / v0.025 / v0.026 / v0.027 / v0.028 / v0.029 / v0.030 / v0.031 / v0.032 / v0.033 / v0.034 / v0.035 / v0.036 / v0.037 / v0.038 / v0.039 / v0.040 / v0.041 / v0.042 / v0.043 / v0.044 / v0.045 / v0.046 / v0.047 → v0.048** для установок нашего
установщика. Узнаются обычные установки с `shop_data` и установки после завершённого
managed-upgrade с отдельным внешним томом и подтверждённой историей активации.
Более старые версии, произвольные Compose-файлы и вручную изменённые привязки требуют
отдельного плана; флага обхода проверок нет. Версия v0.048 повторно не обновляется на себя.

Магазин будет недоступен между остановкой старой версии и отдельной активацией/откатом.
Новый образ собирается до остановки. Старая база остаётся в своём томе; новый снимок
восстанавливается в отдельный новый том, старый образ сохраняется по immutable image ID.
Прокси, VPN-панели, узлы и другие контейнеры не обновляются.

## Команды

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.048/install.sh | bash -s -- --upgrade plan --dir /opt/pushok-vpn
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.048/install.sh | bash -s -- --upgrade prepare --dir /opt/pushok-vpn
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.048/install.sh | bash -s -- --upgrade status --dir /opt/pushok-vpn
```

Bootstrap скачивает фиксированный v0.048 и для новой установки, и для `--upgrade`.
В отличие от bootstrap v0.023, он не подставляет старый целевой релиз v0.022.

Из полного каталога исходников v0.048 можно выполнить те же команды:

```bash
python3 scripts/upgrade.py plan --dir /opt/pushok-vpn
sudo python3 scripts/upgrade.py prepare --dir /opt/pushok-vpn
sudo python3 scripts/upgrade.py status --dir /opt/pushok-vpn
```

`plan` ничего не меняет и не вызывает Docker. Остальным изменяющим действиям нужны root
и доступ к Docker. Для `prepare` нужен один работающий shop, свободное место для образа,
копии и нового тома, а также доступный локальный и публичный `/shop/health`.
Требуется отдельный пароль копии от 16 символов: диалог дважды либо
`--password-file /root/pushok-backup-password` с правами 0600. От root поддержан также
`PUSHOK_BACKUP_PASSWORD`; sudo может не сохранить окружение, используйте файл или диалог.
Пароль не передаётся аргументом Docker и не хранится в журнале.

Сначала сохраните внешнюю резервную копию по BACKUP.md. Во время обновления не редактируйте
`.env`, Compose, installer.json и историю операций. Общий lock исключает параллельную
работу установщика и обновления. Несколько writers одного тома или polling-ботов
по-прежнему не поддерживаются.

## Как выбирается текущая база

| Вид установки | Текущий том | Каталог базы внутри контейнера |
|---|---|---|
| Обычная установка v0.021–v0.047 | `<project>_shop_data` | `/app/data` |
| Завершённый managed-upgrade | Том из managed_upgrade, совпадающий с историей активации | `/app/data/restored` |

Для managed-upgrade проверяются идентификатор операции, сохранённые исходники,
контрольные суммы метаданных/Compose, имя image/volume и завершённая активация.
Фактический mount работающего контейнера должен совпасть с ожидаемым именем тома и быть
доступен самому shop на запись. Нельзя молча выбрать прежний исходный том вместо текущего.

История завершённой активации хранится в `upgrades/<operation>/activation.json`.
У старого v0.022 такого файла не было: при первой подготовке v0.024 подтверждённый
committed-журнал сохраняется туда до замены текущего журнала. `plan` его не создаёт.
Предыдущий журнал также сохраняется в `journal.before.json` новой операции.
При несовпадении существующей истории обновление блокируется.

Незавершённый переход v0.021 → v0.022 **сначала завершите инструментом v0.022**:
пользуйтесь тем же фиксированным bootstrap v0.022 с `--upgrade status/activate/rollback`.
Новый `status` показывает старую операцию, но `prepare`, `activate` и `rollback` не
подменяют контроллер незавершённого перехода другого целевого релиза.

## Подготовка

1. Проверяются версии, исходники, схема установки и совпадение ключа .env с окружением
   работающего shop (без вывода ключа). Создаётся приватный каталог
   `upgrades/<operation>/`, сохраняются метаданные, собирается отдельный новый образ.
2. Останавливается только shop. Помощник без сети видит старый том только для чтения.
   Из выбранного текущего каталога копируются остановленные shop.db и возможный WAL
   во временный writable staging; затем SQLite Backup API создаёт логический снимок.
   Сырое копирование работающей базы не используется.
3. Старым образом создаётся зашифрованная копия всей базы и текущего `.env`. Она
   сохраняется на хосте с правами 0600, читается обратно и проверяется. Ключ не меняется.
4. Копия восстанавливается в `/app/data/restored` нового тома. Браузерные sessions и
   tickets сбрасываются. Новым образом без сети запускаются только init_db и проверка
   расшифровки; worker/бот и запросы к панелям не запускаются.
5. Shop переключается на новый image/volume в `MAINTENANCE_MODE=true`,
   `BACKGROUND_TASKS=false`. После Docker/local/public health журнал получает `ready`.

Лимиты: база до 128 MiB, база вместе с WAL до 256 MiB; tmpfs помощника 768 MiB плюс
память для шифрования и место на диске. Старые тома и образы автоматически не удаляются.
В ready только `/health` доступен, покупки/вход/приватные URL возвращают 503.

## Активация

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.048/install.sh | bash -s -- --upgrade activate --dir /opt/pushok-vpn
```

Активация восстанавливает исходные настройки фоновых задач/обслуживания и пересоздаёт
только shop. При обычных настройках магазин открывается, один worker/бот продолжает
очереди. Явно выключенные фоновые задачи не включаются насильно.
После health-проверок состояние — committed, отдельно сохраняется activation.json.

С начала активации автоматический откат базы запрещён, включая activating и
activation_failed: новые API/worker/бот могли уже записать платежи или изменить узлы.
Сначала сверяйте события и состояние внешних сервисов по аварийной процедуре, не
возвращайте старую базу после новых продаж как обычный откат кода.

## Откат до активации

```bash
curl -fsSL https://raw.githubusercontent.com/mrkoster1988/Shop-VPN-/v0.048/install.sh | bash -s -- --upgrade rollback --dir /opt/pushok-vpn
```

До activate откат возвращает **не исходную когда-то установку**, а текущую перед
подготовкой версию: её image ID, текущий том, DATA_DIR и прежние метаданные. Поэтому
после попытки обновить managed v0.022 возврат идёт в его том с `/app/data/restored`,
а не в старый том v0.021. `.env` и root/source не перезаписываются.

Состояние — rolled_back. Повтор rollback не рестартует магазин. Новая попытка prepare
после отката допускается, если сохранённые подтверждения соответствуют восстановленной
установке. Неудачная сборка также не теряет историю предыдущей завершённой активации.

При ошибке подготовки выполняется попытка такого же отката. Если она не удалась,
состояние recovery_required: устраните причину, проверьте status и выполните rollback.
При прерывании/перезапуске хоста автоматического продолжения нет; журнал сохраняет
намерение и последнюю фазу. Не удаляйте его ради повторного prepare.

`status` показывает операцию, версии, фазу, флаг начала активации и этап ошибки без
пароля/ответов провайдеров. Старые source/volumes/images, копии и история остаются для
восстановления; не удаляйте их и не запускайте Docker prune до полной приёмки.
Симлинки и изменения истории/привязок не обходятся автоматически.

Автоматический Docker-сценарий, его результат и ограничения описаны в DOCKER_STAGING.md.
Локально Docker недоступен; успешность настоящего job оценивается по GitHub Actions.
Прогон использует вымышленные данные и не подтверждает реальные платежи/VPN/публичный
HTTPS на конкретном VPS. Эти проверки по-прежнему необходимы по STAGING.md.
