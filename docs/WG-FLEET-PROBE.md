# Проверка реального трафика WG Fleet

`scripts/wg_fleet_probe.py` запускается на **отдельном Linux-хосте мониторинга**.
Проверка страницы WGDashboard и старые счётчики пользователей не допускают узел
к новым подключениям. Проверяются отдельный технический peer, свежий handshake,
новый обмен байтами, DNS и HTTPS через WireGuard. Загрузка CPU и внешнего сетевого
интерфейса читается с проверяемого узла через отдельный SSH-доступ только для чтения.

## Что подготовить

1. На каждом проверяемом WG создать отдельный технический peer. Он не является
   платной подпиской и не должен использовать ключ действующего пользователя.
2. На независимом хосте создать отдельный network namespace с именем
   `pushok-probe-wg1` и WireGuard-интерфейсом, например `wgcheck1`. В интерфейсе
   должен быть **ровно один** peer с ожидаемым публичным ключом сервера.
3. UDP-сокет WireGuard должен иметь доступ к интернету из исходного namespace:
   стандартный вариант — создать интерфейс на хосте, настроить его и переместить
   в выделенный namespace. Адрес туннеля и default route настраиваются только
   внутри выделенного namespace. Маршрут хоста по умолчанию не меняется.
4. Через туннель должны быть доступны выбранный DNS-сервер IPv4 и собственная
   контрольная HTTPS-страница с ответом `200` или `204`. Страница не должна
   перенаправлять на другой адрес; её сертификат проверяется штатно.
5. Для SSH-метрик подготовить непривилегированного пользователя на WG-хосте,
   ключ без пароля и заранее проверенный `known_hosts`. Python 3 на WG-хосте
   должен читать `/proc/stat` и `/sys/class/net/<внешний интерфейс>/statistics`.
   Скрипт запускает фиксированную программу чтения; команды из конфигурации
   не исполняются. SSH agent forwarding и неизвестные host keys запрещены.
6. Зарегистрировать probe через административный интерфейс и сохранить
   выданный Bearer-токен в отдельный файл. Токен привязан к одному серверу.

Сам probe **не создаёт интерфейсы, не изменяет маршруты и не устанавливает
пакеты**. Требуются `ip`, `wg`, `curl`, `ssh`, Python 3 и разрешения для работы
в подготовленном namespace. DNS-запрос и HTTPS-запрос привязаны к проверяемому
WireGuard-интерфейсу; обнаружение прямого маршрута завершает проверку ошибкой.

## Конфигурация

Пример структуры; идентификаторы и ключ сервера берутся из регистрации и
реальной панели. Значения ниже являются заполнителями.

```json
{
  "schema_version": 1,
  "server_id": "NODE_UUID",
  "server_version": 1,
  "generation": 1,
  "probe_id": "PROBE_UUID",
  "namespace": "pushok-probe-wg1",
  "interface": "wgcheck1",
  "server_public_key": "SERVER_PUBLIC_KEY_BASE64",
  "dns_server": "9.9.9.9",
  "https_url": "https://monitor.example.com/health",
  "https_status": 200,
  "bandwidth_capacity_bps": 1000000000,
  "metrics_ssh": {
    "host": "WG_SERVER_IP",
    "port": 22,
    "user": "pushok-probe",
    "private_key_file": "/secure/wg1-metrics.key",
    "known_hosts_file": "/secure/wg1-known-hosts",
    "interface": "ens3"
  },
  "report_url": "https://pushok.shop/api/admin/wg-fleet/probes/report",
  "token_file": "/secure/wg1-probe.token",
  "state_file": "/secure/wg1-sequence.json"
}
```

Файл конфигурации, SSH private key и Bearer-файл должны принадлежать запускающему
пользователю и иметь права `0600`. Символические ссылки на эти файлы не принимаются.
`bandwidth_capacity_bps` — известная ёмкость канала узла **в битах в секунду**;
скорость внешнего интерфейса должна быть определена оператором, а не угадана
по виртуальной скорости сетевой карты. Выбирать надо физический/внешний
интерфейс узла, чтобы не посчитать один и тот же пакет на нескольких интерфейсах.

```bash
python3 scripts/wg_fleet_probe.py --config /secure/wg1-probe.json
```

Первую проверку можно выполнить без отправки:

```bash
python3 scripts/wg_fleet_probe.py --config /secure/wg1-probe.json --no-submit --report-file /secure/wg1-check.json
```

Вывод содержит только статус, sequence и безопасный код ошибки. Токен, private
key, тело HTTPS-ответа и SSH-диагностика не выводятся. HTTP redirect при отправке
токена запрещён, прокси из окружения не используются. Контрольная HTTPS-страница
запрашивается с новым nonce и без использования локального кэша.

## Интервал и признание результата

Рекомендуемый стартовый интервал — 60 секунд с небольшим разбросом начала для
разных узлов. Это настройка отдельного системного таймера, а не фоновая задача
браузера. Два одновременных запуска для одного state-файла запрещены блокировкой.

- Длительность одной проверки: не более 60 секунд.
- Отчёт при приёме не старше 90 секунд; допустимое расхождение часов 5 секунд.
- Handshake не старше 180 секунд, **и одновременно** положительные приращения
  RX и TX за текущую проверку. Повторный handshake не принуждается разрывом пира.
- Данные допуска узла не старше 180 секунд; возраст handshake повторно проверяется
  при выборе узла. Недоступные метрики также исключают узел из новых назначений.
- Вычисленная нагрузка — максимум доли CPU, большей из входящей/исходящей долей
  внешнего канала и доли занятых/зарезервированных мест. Ровно заполненный узел
  не получает новые назначения. Случайность используется только при точном
  равенстве минимального значения, без допуска «почти минимальная».

Проверка `GET /api/admin/wg-fleet/probes/assignment` перед каждым запуском
обновляет номер описательной версии сервера. Она не может автоматически
изменить `server_id`, `probe_id` или `generation`: смена WireGuard-идентичности
требует новой регистрации и проверки ключа/технического пира. Sequence хранится
на диске и продолжается при обычном изменении версии сервера; при новой
generation начинается отдельная последовательность. Старые и повторные
отчёты отвергаются сервером.

## Границы проверки

Успех с независимого хоста доказывает прохождение выбранных тестов с этой
точки сети. Он не доказывает доступность со всех операторов или телефонов.
Фактическое соединение Flow проверяется отдельно. При пропаже мониторинга новые
назначения прекращаются после срока свежести; это не команда разорвать уже
работающие пользовательские туннели. Для защищённого от единственной точки
отказа мониторинга потребуется отдельное согласование нескольких источников.

Контрактные тесты не подменяют приёмку на работающем WireGuard: до допуска к
выдаче нужно наблюдать реальный успешный отчёт внешнего probe.
