# Бронирование периодов MTProxy — v0.036

Брони создаёт владелец в админке для одобренной заявки с учтённым поступлением.
Рекламодатель видит собственный период и статус, но не внутренние основания,
ID площадки или историю действий. Резерв не запускает узел и не перемещает деньги.
Настройка спонсора и проверка настоящим Telegram-клиентом остаются ручными.

## Создание и отмена

В карточке заявки выберите свободную включённую проверенную площадку, будущую дату/
время и основание. Ввод и отображение времени — в часовом поясе браузера; API хранит
Unix-секунды UTC. Начало должно быть позже времени сервера и не далее 365 дней.
Конец = начало + часы сохранённого тарифа × 3600. Сумма и часы клиентом не задаются.

Интервалы полуоткрытые: [начало, конец). Смежные периоды разрешены, пересекающиеся
неиспользованные брони одной площадки запрещены. Проверяются все такие брони,
а не только текущая страница списка. В этой версии площадка с фактически активным
или приостановленным размещением не принимает новые брони даже на далёкое будущее:
его реальное окончание заранее не гарантируется.

Начиная с v0.037 перенос выполняется одним действием без предварительной отмены.
Отмена с повторным резервом также доступна как отдельный сценарий.
Первоначальное и последующие окна сохраняются в снимках истории.
Истечение окна старта само по себе не отменяет бронь. Её можно отменить, в том числе
перед полным возвратом, или затем зарезервировать новый период.
Использованную при запуске бронь отменить нельзя: дальше действует размещение.

## Связь с запуском и паузой

Ручной запуск по брони разрешён на её площадке, начиная с starts_at и строго до
ends_at, с актуальной booking_version. Ранний запуск не расходует бронь; истёкшее
окно требует отмены/переноса. После проверки бронь атомарно становится consumed
в одной транзакции с созданием размещения. Повтор UUID не использует её второй раз.

Поздний запуск сохраняет полную длительность тарифа, поэтому его фактический срок
может быть позже исходного планового конца. Он разрешён только если весь новый
интервал не пересекает другую неиспользованную бронь. Если следующая бронь начинается
сразу после планового конца, поздний запуск будет отклонён. Владелец должен согласовать
перенос или другую площадку, а не уменьшать оплаченный срок незаметно для клиента.
Фактический план остановки хранится в placement.expected_stop_at; прежнее окно
планирования остаётся в booking.starts_at/ends_at.

Запуск без брони тоже проверяет весь тарифный период против будущих резервов.
Продолжение после паузы проверяет оставшееся время против следующих броней.
Пауза удерживает физическую площадку; следующая бронь не может запуститься, пока
предыдущее размещение реально не остановлено и владелец не подтвердил finished.
Плановый срок или истёкший бюджет не освобождает площадку автоматически.
Бронь не является командой узлу и не защищает от действий людей вне магазина:
перед ручным переключением обновляйте данные и проверяйте фактическое состояние.

## Админка

Раздел «Брони MTProxy» показывает неиспользованные, просроченные или все брони,
по 20 строк с упорядочением по началу и ID заявки. Здесь доступны отмена и запуск
в допустимом окне. Создать первый резерв можно в одобренной оплаченной заявке.
Просроченные записи в общем списке не исчезают автоматически.
Список обновляется явно, при смене страницы/фильтра и после успешного действия.
Выход очищает намерения, ошибка чтения убирает прежние формы, поздние ответы
не заменяют новый список. После потери ответа повторяется исходный UUID.

## API

Все пути относительны PUBLIC_URL своей установки. Требуется ADMIN_TOKEN и общая
проверка Origin для изменений; отдельного клиентского API управления бронью нет.

| Метод и путь | Назначение |
| --- | --- |
| GET /api/admin/ads/bookings?view=reserved&page=1 | Список: reserved, expired, all |
| POST /api/admin/ads/requests/{id}/booking/reserve | Резерв или повторный резерв после отмены |
| POST /api/admin/ads/requests/{id}/booking/reschedule | Перенести неиспользованную бронь атомарно |
| POST /api/admin/ads/requests/{id}/booking/cancel | Отмена неиспользованного резерва |

Общие поля POST: operation_id (UUID), request_version, payment_version,
booking_version (0 до первой брони), note (закрытое основание).
Для reserve также нужны site_id, site_version, starts_at. Для cancel они не нужны.
Текущая версия увеличивается при резерве, отмене и использовании при запуске.
Повтор идентичного UUID возвращает текущую бронь без новой записи, даже после отмены;
другие данные под тем же UUID дают 409. Старые версии и конфликты — 409,
некорректный ввод — безопасный 422. Частные основания в ошибках не отражаются.

POST placement/start дополнительно принимает booking_version, если есть reserved.
В остальных подтверждениях версия брони не передаётся. При отсутствии брони прежний
запуск остаётся совместимым, но проверяет будущие периоды.
Неиспользованный резерв блокирует учёт полного возврата до отмены.

В собственных заявках booking содержит state (reserved/canceled/consumed), version,
site_name, starts_at, ends_at, updated, expired, can_start. Последний признак означает
только попадание в окно старта: оплата, свободная площадка и пересечения всё равно
проверяются повторно. Административная сводка дополнительно содержит site_id и
последние 20 действий с закрытыми основаниями и снимками периодов.
Весь журнал сохраняется в базе; общий ADMIN_TOKEN пока не различает сотрудников.

## Данные и приёмка

Добавлены ads_bookings и ads_booking_actions. Прежние строки/столбцы не меняются.
Пересечения reserved проверяются в BEGIN IMMEDIATE и триггерами INSERT/UPDATE
SQLite. Проверка физической занятости и атомарные гонки выполняются в той же
транзакции. Старые отпечатки команд размещения без booking_version сохраняются:
обновление не ломает повтор команды до v0.036.

Зашифрованный архив сохраняет резерв и снимки истории; сессии удаляются при
восстановлении по общему правилу. Новые пустые таблицы исключены только из сравнения
данных со старой схемой; наличие проверяется отдельно, непустые записи входят в хеш.
После восстановления владелец сверяет расписание и фактический спонсорский канал.

Проверки используют искусственные часы и синтетические подтверждения. Docker
проверяет реальные HTTPS-запросы резерва, отмены, повторного резерва и использования,
а также восстановление архива. Реальный показ, подписчики, банковские операции
и прибыль этим выпуском не измеряются.


## Дополнение v0.037: перенос без потери исходного места

reschedule принимает те же поля, что reserve, с текущей booking_version.
Разрешены только reserved, включая истёкшее окно старта, без начатого размещения,
при актуальном одобрении и поступлении. Новый период должен быть в будущем;
целевая площадка — свободной, включённой и проверенной. Тариф и сумма не меняются.
Проверка нового интервала исключает собственную прежнюю бронь, поэтому можно
сдвинуть период с частичным пересечением своего прежнего окна.

При конфликте периода, старой версии, занятой площадке или ошибочном вводе прежняя
бронь и журнал не меняются. Успешный перенос увеличивает версию ровно на один,
записывает reschedule и снимок нового периода, сохраняя прежние записи.
Повтор исходного operation_id возвращает текущую бронь без второго изменения,
даже после последующей отмены. Другой запрос под тем же UUID — 409.

Владелец выбирает «Перенести бронь одним действием» отдельно от отмены.
Это изменение плана; команды узлу, списания и возвраты не выполняются.
После потери ответа повторяется UUID, после конфликта следует обновить данные.

Миграция расширяет CHECK таблицы ads_booking_actions: копирует прежние строки
в транзакции с сохранением rowid, отпечатков и JSON-снимков, затем заменяет таблицу.
Состав и значения столбцов не меняются, повторная миграция ничего не переписывает.
Дополнительные пользовательские столбцы, индексы и триггеры старой таблицы не
удаляются: такая схема отклоняется до замены и требует отдельного плана обновления.
