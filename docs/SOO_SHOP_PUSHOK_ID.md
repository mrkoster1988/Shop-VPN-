# SOO Pushok — доверенная авторизация Shop через Pushok ID, контракт v1

**Статус:** Shop реализует принимающую сторону и интерфейс; центральный Pushok ID должен реализовать issuer и отдельное подтверждение с действующей сессией. Пока обе стороны не прошли CI и совместную приёмку, интеграция выключена. Существующие MTProxy identity bridge и локальные способы входа Shop не заменяются.

## Настройка доверия

Для конкретного магазина разработчик регистрирует в Pushok ID неизменяемый HTTPS-адрес Shop (включая /shop), уникальный audience и отдельный 32-байтовый HMAC-ключ. В Shop:
- SHOP_PUSHOK_ID_PORTAL=https://auth.pushok.shop
- SHOP_PUSHOK_ID_AUDIENCE=pushok-shop:<16–64 буквенно-цифровых символов, _ и ->
- SHOP_PUSHOK_ID_SECRET=<64 lowercase hex, отдельные случайные 32 байта>

Секреты только на серверах. Не использовать JWT_SECRET, токен бота, ключ MTProxy или ключ другого магазина. ID хранит allowlist audience → точный HTTPS endpoint и ключ; запрещены callback URL, подставляемые браузером, динамические хосты и redirects. В /admin → Pushok ID разработчик явно включает интеграцию. Регистрация новых аккаунтов — отдельный OFF по умолчанию. Смена конфигурации приостанавливает доверие до сохранения обновлённой политики; сохранение другой конфигурации удаляет старые ID-сеансы и запросы. Не возвращать старый секрет после ротации.

## Обмен

1. Browser Shop POST /api/auth/pushok-id/start, JSON {"mode":"signin"} для анонимного пользователя или {"mode":"link"} для действующего Shop-аккаунта с подтверждённым Telegram. Shop создаёт случайный 32-byte request (base64url без padding) и независимую browser cookie shop_id_request (Secure, HttpOnly, SameSite=Lax, path установки, 300 секунд). Сохраняются только хеши и срок. Ответ: state=pending, expires_at, approval_url. URL содержит только shop_request и shop_audience.
2. ID открывает запрос из зарегистрированного магазина, проверяет собственную **действующую, не отозванную** сессию, получает UUID пользователя и его подтверждённый Telegram numeric subject из серверной БД, показывает название магазина, домен, Telegram ID и UUID, требует явное согласие. Нельзя принимать эти сведения из формы пользователя, username, display name или email. Для этого контракта отсутствие подтверждённого Telegram ID означает отказ.
3. После согласия ID сервер формирует канонический ASCII JSON (sort_keys=True, separators=(',',':'), ensure_ascii=True) со строго следующими полями: {"v":1,"iss":"pushok-id","aud":"pushok-shop:<registered>","purpose":"shop_identity","request":"<shop_request>","sub":"<canonical lowercase UUID>","tg":<integer 0 < tg < 2**52>,"iat":<Unix seconds>,"exp":<iat+60>}.
   Подпись: lowercase hex HMAC-SHA256(key=bytes.fromhex(secret), message=b'pushok-id-shop-approval-v1\0'+canonical_bytes).
   proof = "pid1." + base64url(canonical_bytes без "=") + "." + signature.
   ID делает HTTPS POST к зарегистрированному Shop /api/auth/pushok-id/approve, JSON {"proof":"..."}. TLS-проверка обязательна, redirects запрещены. Не логировать тело/подпись, не возвращать proof в браузер. Успех {"ok":true}; 401 неверное доказательство, 409 запрос истёк/использован, 503 отключено. Потерянный ответ — пользователь проверяет статус в Shop, новый proof не может изменить уже подтверждённую личность.
4. Browser в исходной вкладке вручную проверяет GET /api/auth/pushok-id/status с cookie. Ответ missing, pending или approved (confirmation, subject, telegram_id, mode, expires_at). Он не содержит пароля, токена ID или ключа VPN. Пользователь сверяет Telegram ID и UUID, подтверждает POST /api/auth/pushok-id/finish {"confirmation":"<returned>","subject":"<returned UUID>","confirm":true}. Shop транзакционно проверяет запрос, cookie, режим, сессию, срок, конфликты уникальности и текущую политику.
5. Для link требуется тот же локальный сеанс и точно тот же verified Telegram ID. Для signin Shop использует существующий аккаунт с этим Telegram ID либо создаёт новый, если владелец разрешил регистрацию. Никакого автоматического слияния email-аккаунтов, копирования кошельков, заказов, ролей или изменения Telegram ID. Один UUID ↔ один Shop user_id ↔ один Telegram ID. Конфликты требуют отдельного разбирательства.
6. Успешный signin создаёт **только** локальную Shop cookie session на 3600 секунд, не выдаёт токен ID, не даёт staff-права. Link сохраняет обычный сеанс. Авторизованная выдача использует действующие правила Shop, включая существующую опциональную стартовую выдачу WG; этот контракт сам не создаёт платных подписок. POST /api/auth/pushok-id/cancel удаляет запрос. POST /api/auth/pushok-id/revoke под Shop-сессией отзывает её ID-сеансы, сохраняя связь и подписки. Отключение доверия также отзывает все такие сеансы. Центральный отзыв ID-сессии после обмена не синхронизируется мгновенно; срок локального сеанса ограничен одним часом.

## Кошелёк и управление

В текущем Pushok ID API wallet возвращает not_activated, balances_available=false. В Shop отображается not_connected, без выдуманных нулей, сумм, конвертации Stars или общего баланса. Финансовый журнал Shop не является кошельком; привязка аккаунтов не переносит историю денег и не открывает платёжный API. Роли Shop назначаются отдельно. Раздел интеграции доступен только разработчику.

## Приёмка и эксплуатация

Четыре новые таблицы: shop_id_policy, shop_id_links, shop_id_requests, shop_id_sessions. В старой установке они пустые; обычные cookie остаются совместимыми. Архив сохраняет policy/link; восстановление удаляет запросы и все сеансы, включая производные ID-сеансы. До запуска после восстановления сверить актуальность привязок и ключей с центральным сервисом. При откате на старый бинарник использовать штатное восстановление с очисткой сеансов; не запускать два worker.

Проверить на стенде: независимый ключ и audience, подпись и срок, ошибка чужого Telegram ID, повтор, одновременное переключение аккаунта, отказ создания нового аккаунта по умолчанию, отзыв, управление настройками, реальные браузеры/Mini App, отсутствие токенов в логах и кэше. Тесты Shop используют синтетический подписанный fixture, не доказывают существование центрального issuer. Реальную авторизацию и кошелёк принимать отдельными интеграционными этапами.
