# WGDashboard: первый этап адаптера

Реализована отдельная проверка API без изменения peers. Выдача, продление и отзыв
через WGDashboard ещё не подключены к заказам или реестру серверов.
Действующий WG-агент продолжает работать по собственному контракту.

Контракт изучен по исходникам WGDashboard, commit
`8d21152947167e4b3bdd005c52b3b71125b723a9`:
https://github.com/WGDashboard/WGDashboard/blob/8d21152947167e4b3bdd005c52b3b71125b723a9/src/dashboard.py
и `src/modules/WireguardConfiguration.py` того же commit.
Запрос: GET `/api/getWireguardConfigurations`, ключ в `wg-dashboard-apikey`.
Требуются `status: true`, единственный интерфейс с выбранным `Name`,
`Protocol: wg` и `Status: true`. Доступность API сама по себе не подтверждает
аутентификацию: панель может иметь отключённую защиту.

Создайте JSON-файл профиля с правами 0600 от текущего пользователя:

```json
{"url":"https://dashboard.example/prefix","token":"YOUR_API_KEY_AT_LEAST_32_CHARACTERS","configuration":"wg0"}
```

`url` содержит префикс панели, без `/api`. В WGDashboard включите API и создайте
отдельный ключ. Не помещайте ключ в аргументы команд или публикуемые отчёты.

```bash
chmod 600 /secure/wgdashboard.json
python scripts/panel_check.py --wgdashboard --profile-file /secure/wgdashboard.json --output /secure/wgdashboard-check.json
```

Отчёт создаётся без перезаписи, права 0600. Код завершения 0 — контракт чтения
подтверждён; 1 — ошибка API; 2 — ошибка локальных параметров. TLS проверяется,
редиректы и прокси окружения отключены. JSON панели может содержать приватные
ключи: отчёт возвращает только флаги, без содержимого ответа или текста исключений.

Проверки на HTTP-фикстурах покрывают неизвестный формат, недоступный интерфейс,
ошибки HTTP, неверный профиль и отсутствие записи. Реальная панель не проверялась.
Следующий этап: постоянная идентичность peer, восстановление после потерянного
ответа, выдача конфига, подтверждение продления и отзыва; затем стенд VPN-трафика.


## Второй этап: методы создания и удаления peer

В адаптере реализованы `ensure_peer(client, private_key, name)` и
`revoke_peer(client, public_key)`. Они пока не вызываются обработчиками заказов.
`ensure_peer` требует заранее сохранённый приватный X25519-ключ, вычисляет публичный
ключ и проверяет наличие peer до и после создания. Повтор после потерянного ответа
использует тот же ключ. Отдельная ограниченная запись не включается автоматически.
При удалении проверяется отсутствие peer как в активном, так и в ограниченном списке.
Успех HTTP без подтверждения состояния не считается выполненной операцией.

Это не законченная интеграция продаж: пока нет сохранения ключа в жизненном цикле
заказа, выдачи файла конфига, продления, планирования окончания срока и проверки
трафика. Клиент для методов записи должен запрещать редиректы и прокси окружения,
проверять TLS и задавать таймаут. Конкурирующие записи для одного ключа должен
сериализовать вызывающий код. Ошибка транспорта после записи требует повторного
чтения; новый ключ при повторе создавать нельзя. Контракт подтверждён фикстурами,
реальная панель пока не проверялась.


## Третий этап: постоянные ключи и загрузка конфига

`stored_private_key(server_id, credential_id)` сохраняет ключ в таблице
`wgdashboard_keys` с шифрованием штатным `ENCRYPTION_KEY`. Пара сервер/UUID
идентичности уникальна, создание сериализовано транзакцией SQLite. Повтор и
повторная инициализация базы сохраняют прежний ключ. Неизвестный сервер,
VLESS-сервер или неверный UUID отклоняются. Ключ не удаляется при отзыве peer:
он необходим для сверки и восстановления после неопределённого ответа панели.
Потеря `ENCRYPTION_KEY` означает потерю доступа к сохранённым ключам.

`download_config(client, private_key)` сначала подтверждает активный peer, затем
читает `/api/downloadPeer/<configuration>?id=<public_key>`. Проверяются размер,
секции, совпадение приватного ключа, IP-адреса, серверный публичный ключ и endpoint.
Неизвестные поля и исполняемые hooks отклоняются; имя файла от панели не используется.
Возвращаемый текст содержит секрет: его нужно шифровать и выдавать только владельцу.

Методы ещё не подключены к заказам. Срок доступа, продление, поведение ротации,
серверный профиль в админке и проверка реального трафика остаются открытыми этапами.
Тесты используют фикстуры API и временную SQLite, без обращения к реальной панели.


## Четвёртый этап: подключение к заказам через API реестра

В профиле сервера `protocol=wg` теперь можно явно указать
`settings={"api":"wgdashboard","url":"https://dashboard.example/prefix",
"token":"YOUR_API_KEY_AT_LEAST_32_CHARACTERS","configuration":"wg0"}`.
Создавайте сервер через штатный административный API, проверяйте API и только затем
включайте приём новых заказов. Форма выбора WGDashboard в админке ещё не добавлена.
Существующие профили без `api` остаются профилями WG-агента. Неизвестный режим
отклоняется. При наличии подписок URL, режим API и интерфейс менять запрещено.

Оплаченный заказ сохраняет ключ до первой сетевой записи, создаёт/находит peer,
скачивает проверенный конфиг и шифрует его штатным сценарием выдачи. Продление
повторно использует прежний ключ; дополнительные устройства используют собственный
UUID. Worker магазина отзывает peer по окончании срока. При потере сохранённого
ключа отзыв возвращает ошибку, а не создаёт замену и не сообщает ложный успех.

**Срок на стороне WGDashboard пока не планируется.** При остановленном магазине или
недоступной панели peer может оставаться активным после срока. Этот режим не следует
считать готовым к продажам до серверного ограничения срока и реальной приёмки.
Тест оплаченного заказа, продления и истечения срока использует имитацию адаптера;
контракт HTTP проверяется отдельно фикстурами. Реальная оплата и VPN-трафик не проверены.
