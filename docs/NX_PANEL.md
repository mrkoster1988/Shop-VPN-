# NX Panel: диагностика и контракт интеграции

[← Технологии](TECHNOLOGIES.md) · [Установка NX](https://docs.nx-panel.org/start/install-panel) · [Официальная документация](https://docs.nx-panel.org/)

**Статус: реализована предварительная диагностика API. Выдача и продажа через NX
ещё не подключены.** Проверки на ответах HTTP-стенда не подтверждают работу реальной
панели, узлов и VPN-клиента. NX устанавливается отдельно по выбору владельца.

Этот режим добавлен в `main` после v0.055; установочный архив v0.055 его не содержит.
Для команд ниже нужен обновлённый checkout Shop с установленными `requirements.txt`.

## Проверить подключение

1. Завершите мастер установки NX и настройте HTTPS. Для собственного CA передайте
   `--ca-file`; отключения проверки сертификата нет.
2. В NX откройте **Access → API tokens**. Для диагностики достаточно
   `users:read` и `templates:read`, в пределах прав выбранного администратора.
   Поле Addon id оставьте пустым. Токен без ограничений будет отмечен предупреждением.
3. Выберите существующий шаблон и запишите его числовой ID. Диагностика подтверждает
   только доступность шаблона, не его протоколы, назначение узлам или реальный трафик.
4. Под текущим пользователем создайте приватный файл вне репозитория:

```bash
install -m 600 /dev/null /root/nx-check.json
nano /root/nx-check.json
```

Пример содержимого; замените адрес, токен и ID своим значением:

```json
{
  "api": "nxpanel",
  "url": "https://nx.example.com/panel-path",
  "token": "REPLACE_WITH_YOUR_API_TOKEN",
  "template_id": 7
}
```

`url` — HTTPS адрес панели с её base path, **без** `/api` или `/api/v1`.
Токен хранится в файле, не передаётся аргументом командной строки.
Симлинки, чужой владелец, права кроме 0600 и размер свыше 16 KiB отклоняются.

```bash
.venv/bin/python scripts/panel_check.py --nxpanel \
  --profile-file /root/nx-check.json --output /root/nx-check-report.json
```

Отчёт создаётся с правами 0600 без перезаписи. Также поддерживается
`--profile-stdin`. `--server` для NX пока недоступен: профили NX не добавляются
в реестр серверов продаж. Режимы `--nxpanel` и `--wgdashboard` взаимоисключающие.

Проверка выполняет `GET /api/v1/me`, `GET /api/v1/users?limit=1&offset=0`
и постраничное чтение `/api/v1/templates` до выбранного ID. Максимум десять
страниц по 100 шаблонов, максимум 1 MiB на ответ, тайм-аут запроса 20 секунд.
Редиректы запрещены; прокси из окружения не используются. Ответы с данными
пользователей и секретами шаблонов не записываются в отчёт.

## Как читать результат

| Результат | Значение и действие |
| --- | --- |
| `api_checks_ok`, exit 0 | Токен, права чтения, схема списка пользователей и доступность шаблона подтверждены |
| `NXUnrestrictedToken` в warnings | Токен не ограничен scopes; выпустите отдельный токен с нужными правами |
| `AuthenticationRejected` | Проверьте токен, его срок, роль и разрешения владельца |
| `NXReadScopesRequired` | Не хватает права чтения пользователей или шаблонов |
| `NXResellerUnavailable` | Реселлер заблокирован либо его состояние не подтверждено |
| `NXTemplateNotFound` | Шаблона нет среди доступных этому токену |
| `NXTemplateListChanged` | Список изменился во время обхода или содержит повторяющиеся ID; повторите проверку |
| `NXTemplateScanLimit` | ID не найден за десять страниц; результат не считается успешным |
| `NXRateLimited` / `NXLicenseLimit` | Панель вернула 429 / 402; проверка не повторяет запрос автоматически |
| `UnsupportedNXSchema` / `UnsupportedNXIdentity` | Ответ не соответствует проверяемому контракту; нужна сверка версии панели |
| `NXResponseTooLarge` | Ответ превысил установленный предел |
| `needs_attention`, exit 1 | Внешняя проверка не завершена успешно; причина в `error_code` |
| `invalid_input`, exit 2 | Ошибка профиля, локального файла, CA или аргументов |

Успех **не подтверждает** права записи, лицензионный запас, состояние узлов,
выдачу, продление, отзыв, VPN-трафик, оплату или установку VPS. Эти поля scope
остаются `false`. Диагностика не включает продажи и не меняет БД магазина.

## Контракт следующего этапа

Ниже спецификация для разработки, а не уже работающие методы магазина.
Начальный сценарий — один явно выбранный шаблон VLESS и фиксированный срок.

| Операция Shop | API NX | Условия подтверждения |
| --- | --- | --- |
| Создать доступ | `POST /api/v1/users` | Сохранить намерение и неизменный payload до отправки; использовать постоянный `Idempotency-Key`; сохранить ID NX, затем прочитать пользователя и проверить идентичность, шаблон, `enable`, `expiry`, `duration=0`, `licensed` и безопасный `subUrl` |
| Продлить до даты Shop | `GET`, затем `PATCH /api/v1/users/{id}` | Передать абсолютный `expiry` в Unix-секундах и `version=updatedAt`; не заменять весь объект; сохранить credentials, лимиты и счётчики; подтвердить чтением |
| Отключить | `PATCH /api/v1/users/{id}` с `enable=false` | Проверить сохранённую идентичность, подтвердить отключение; отдельно закрыть сессии через `/connections/close` и проверить узлы |
| Повторить после сбоя | Чтение сохранённого ID и сверка операции | Повтор не создаёт вторую учётную запись и не добавляет срок второй раз |
| Получить событие | Webhook NX | Проверить HMAC по исходным байтам и время, дедуплицировать `X-Nx-Delivery`, уточнить состояние через API |

Особенности, которые должны попасть в реализацию и тесты:

- NX выдаёт числовой ID пользователя. Нужна отдельная постоянная связь
  `(сервер Shop, подписка Shop) → ID NX` и идентификатор операции.
  Произвольный результат текстового поиска не доказывает принадлежность клиента.
- Кэш `Idempotency-Key` живёт **24 часа**. После потери ответа и истечения этого
  срока нельзя слепо повторять создание: требуется однозначная сверка, иначе
  операция остаётся для ручного разбора. Ключ связан с методом, маршрутом,
  query и телом, поэтому payload незавершённой операции должен быть неизменным.
- `PATCH` поддерживает версию. После 409 нужно перечитать запись и заново
  проверить условия; параллельное изменение не должно быть затёрто.
- NX также имеет `POST /api/v1/users/renew/{id}` с добавлением дней. Для Shop
  выбран абсолютный срок: очередь повторов не должна повторно начислять дни.
- Ручная блокировка отличается от отключения по сроку/квоте. Оплата не должна
  молча снимать административную блокировку. Политика восстановления требует
  отдельного решения и теста.
- Права `users:write` нужны только будущему адаптеру выдачи. Диагностика их
  не запрашивает и не подтверждает. Не нужны `backup:read`, `nodes:install`
  или права управления токенами.

## Приёмка на отдельном стенде

1. Зафиксировать версии Panel/Node и их OpenAPI, создать отдельный шаблон и токен.
2. Проверить read-only диагностику и отказ для неверных прав/шаблона/сертификата.
3. После реализации записи: создать клиента, потерять ответ, повторить запрос;
   убедиться, что запись одна, связь с Shop сохраняется после перезапуска.
4. Продлить, повторить оплату и задачу выдачи; проверить прежние credentials,
   отсутствие двойного начисления, гонку версий и сохранение лимитов.
5. Проверить отключение активного VPN-соединения, недоступный узел и восстановление.
6. Проверить лицензионный отказ, 429, потерю связи с панелью и отсутствие
   ложной готовности заказа. Подтвердить трафик выбранным реальным клиентом.

## Эксплуатационные ограничения и источники

По актуальной документации на 12.11.2026 бесплатный предел — 50 пользователей
и 2 узла. Истечение лицензии или 14 дней без связи с её сервером переводит
панель на бесплатный предел; сверхлимитные записи перестают обслуживаться.
Узел останавливает ядро через три минуты без связи с панелью. Это требует
контроля доступности панели и проверки восстановления до платных продаж.

Основная панель распространяется готовыми сборками с закрытым исходным кодом.
Shop остаётся самостоятельным продуктом; установка NX не обязательна.
