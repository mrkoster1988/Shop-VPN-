## 2. Конкретные блокеры

### P0 — красные проверки выпуска

**Python.** `tests/test_wgdashboard_orders.py::test_interface_cannot_change_after_subscription_is_bound` создаёт `SimpleNamespace` без новых полей `schedule_expiry` и `panel_timezone`. `app/servers.py:224` обращается к ним, и тест получает `AttributeError` вместо ожидаемого HTTP 409. Ошибка воспроизведена локально и в CI. Нужно привести тест к актуальной модели запроса, сохранив проверку запрета смены интерфейса у связанной подписки. Сам по себе этот сбой не доказывает дефект реального HTTP-запроса.

**Docker.** `tests/docker_staging.py` останавливается после запуска базовой v0.021: среди добавленных таблиц есть `wgdashboard_expirations`, которой нет в `allowed_new` функции `compare`. В сообщении `changed=` и `missing=` пустые. Это расхождение контрольного списка с новой миграцией, а не доказанная потеря данных. Нужно проверить схему и ожидаемые начальные данные, дополнить проверки миграции и пройти весь сценарий обновления, отката и восстановления. Отключать сравнение данных нельзя; последующие этапы этого прогона ещё не подтверждены.

### P0 — исходники не равны установочному релизу

`install.sh` загружает архив **v0.054**, а новые подсказки, выбор установки панелей и последние изменения API находятся в `main` после релиза. Скачивание самого install.sh из main не меняет закреплённый архив.

До публикации нового проверенного релиза нельзя обещать, что пользователь получит все последние функции одной командой. [Краткая инструкция](INSTALL_QUICKSTART.md) уже предупреждает об этом.

### P0 — не пройден полный путь покупателя на целевой инфраструктуре

Нужна подтверждённая цепочка: вход → тариф → платёж → единственная выдача → импорт → реальный VPN-трафик → продление → отключение. Отдельно: повтор webhook, потеря ответа панели, перезапуск Shop и восстановление копии.

Проверка API или зелёный /health недостаточны для объявления магазина готовым к продажам.

## 4. Что мешает считать установку панелей готовой «под ключ»

1. Мастер требует вручную скопировать digest официального образа. Утверждённого проверенного набора версий в нём нет.
2. Он вызывает `docker compose up -d`, но не проверяет полноценную готовность панелей/API и VPN.
3. Для повторного запуска требуется новый каталог. После частичного сбоя автоматическое продолжение не реализовано.
4. В основном мастере панели устанавливаются до подключения маршрутов Nginx и финальной проверки публичного HTTPS. Ошибка необязательной панели прервёт эту часть установки Shop; требуется явный путь продолжения.
5. Порты закреплены: 2053/8443 для 3x-ui и 10086/51820 для WGDashboard. Занятый порт останавливает мастер; выбора альтернатив в диалоге пока нет.
6. Inbound, TLS/REALITY, API-ключи, интерфейс WG, NAT и подключение панели в Shop требуют ручной настройки. SSH-туннель описан, но для новичка с телефоном нужен проверенный подробный сценарий.
7. Бэкап Shop содержит БД магазина и .env, а не тома новых панелей. Их восстановление должно проверяться отдельно.
8. Инструкция новых панелей предлагает настроить 2FA. При этом Legacy-адаптер Shop не вводит OTP: перед включением продаж нужно выбрать реально совместимый API-режим конкретной версии, а не обещать универсальный вход.

Для уже работающей 3x-ui на pushok.shop новый установщик панели не требуется: выбрать «0», оставить её адрес, настроить Shop в /shop и подключить существующий API.

## 5. Порядок подготовки к запуску

1. **Исправить два красных направления CI.** Актуализировать WGDashboard-тест и строгие ожидания миграций. Получить зелёный полный CI, включая Docker upgrade/rollback/restore и WireGuard.
2. **Подготовить проверенный установочный выпуск.** Согласовать номер версии загрузчика, приложения, CHANGELOG и инструкций; удостовериться, что архив релиза содержит новые функции.
3. **Пройти чистую Ubuntu 24.04 и существующий прокси.** Проверить загрузку install.sh, подготовку ОС, Docker, диалог, /shop, DNS/TLS, перезапуск, занятые порты и повтор после сбоя. Для существующей 3x-ui — сохранить её маршруты.
4. **Пройти сквозную приёмку магазина.** Сначала одна выбранная панель; затем остальные перед объявлением их поддержанными на запуске. Проверить оплату, дубли/ошибки, фактический трафик, продление/истечение, уведомления, SMTP и восстановление. Зафиксировать дату, версии и очищенные результаты по [STAGING.md](STAGING.md), [SBP_PAYMENTS.md](SBP_PAYMENTS.md), [DOCKER_STAGING.md](DOCKER_STAGING.md).
5. **Завершить поставку новых панелей и эксплуатацию.** Проверенные образы, понятные подсказки, health-проверки, продолжение после ошибки, инструкция API и резервирование томов.
6. **Довести бренд и согласованные расширения отдельными этапами.** Сохранить в плане акции/купоны, Pushok ID/кошелёк, Edge Glow и объединение проектов. Покупку Stars начинать только после подтверждения поставщика. Matrix остаётся вне текущей разработки.

MVP не требует одновременно завершить общий кошелёк, продажу Stars и Matrix. Но функции, показанные покупателю и включённые в продажах, должны пройти свою приёмку. Рефералку и необязательные интеграции не считать готовыми только по наличию кнопок.

## 6. Условия решения «можно запускать»

- [ ] Зелёные проверки именно выпускаемого коммита.
- [ ] Новая команда установки получает проверенный релиз со всеми заявленными изменениями.
- [ ] Чистая установка и совместная работа с существующей панелью подтверждены.
- [ ] Реальный платёж даёт ровно одну подписку; неподтверждённый — не даёт.
- [ ] На клиентском устройстве подтверждены VPN, продление и отключение.
- [ ] Проверены ошибка панели, повтор, перезапуск и восстановление.
- [ ] Описан и проверен порядок возвратов, поддержки и корректировки бонусов, если они включены.
- [ ] Пройдена мобильная приёмка сайта и Telegram Mini App.
- [ ] Зафиксированы версии, результаты и известные ограничения без секретов.

Текущая конфигурация — SQLite и один процесс приложения с фоновыми задачами внутри него. Готовность к нескольким worker-процессам или горизонтальному масштабированию этим отчётом не подтверждается.
