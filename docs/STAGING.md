# Стендовая приёмка Shop VPN

Эта процедура ещё не выполнена на реальной инфраструктуре. Используйте отдельный
стенд, тестовые учётные записи и резервные копии. Доступ к production не требуется.

## Состав

Магазин по /shop с отдельной SQLite, панель для Legacy, панель для Clients JSON,
WG-агент и клиентское устройство. Для каждого узла запишите версию установленного
ПО и выбранный режим API, не включая токены, конфиги и приватные ключи в отчёт.
Подготовьте один рабочий VLESS inbound на каждой панели. Не используйте чужие
клиентские записи в качестве тестовых.

## Последовательность

1. Запустите магазин с пустой базой. Добавьте три выключенных сервера в админке.
   Проверьте каждый API и включите приём. До успешной проверки включение должно
   давать отказ. Убедитесь, что реквизиты не возвращаются в ответах API магазина.
2. Оставьте активной первую панель. Зарегистрируйте покупателя, оформите заказ с
   ручной оплатой и подтвердите его после тестовой проверки. До подтверждения
   ключ не выдаётся. После выдачи сохраните локально UUID и время окончания.
3. Импортируйте конфиг на устройстве, проверьте доступ в интернет через туннель.
   Зафиксируйте время и результат проверки без публикации конфигурации.
4. Переведите первую панель в «только продления» и включите вторую. Продлите первого
   покупателя: сервер и UUID должны сохраниться, дни добавиться к прежнему сроку.
   Новый покупатель получает доступ через вторую панель.
5. На Clients JSON повторите покупку, импорт и продление. В самой панели проверьте
   единственную запись служебного email, UUID магазина и правильный inbound.
   Настройки существующего клиента должны сохраниться после продления.
6. Имитируйте потерю ответа после создания клиента на отдельном тестовом прокси.
   Перезапустите магазин и дождитесь повтора: второй ключ не создаётся, срок не
   начисляется повторно. Затем восстановите обычное соединение и проверьте трафик.
7. Задайте лимит одной подписки на пустом тестовом сервере. Новый клиент после
   заполнения места не должен назначаться на него, продление существующего доступно.
   Если пул заполнился после оплаты, заказ остаётся оплаченным в очереди.
8. Проверьте неверный токен, недоступный endpoint, редирект и неподходящий API.
   Ошибка не должна приводить к смене режима, ключа, сервера или раскрытию секретов.
   Восстановите профиль, проверьте API и повторите выдачу из админки.
9. Для WG проверьте импорт .conf, QR, интернет, продление с тем же ключом/IP и
   отзыв тестового peer после истечения срока.
10. Восстановите копию базы прежней версии с прежним .env: старые подписки получают
    исходную привязку. Повторный запуск с изменённым .env не переносит их.
    Без полного исходного профиля миграция должна откатиться и остановить запуск.
11. Восстановите базу и ключ шифрования из резервной копии. Проверьте вход,
    очередь, скачивание своего конфига и отсутствие доступа к чужим подпискам.

## Результат

Для каждого пункта сохраните дату, версии, ожидаемый/фактический результат и
идентификатор тестового заказа. Прикладывайте только очищенные логи. В отчёте
разделяйте доступность API и фактическое прохождение VPN-трафика. Непройденный пункт
остаётся блокером выпуска на сервер, даже если автоматические тесты проходят.

## Лимиты тарифов — v0.014

Создайте тарифы с лимитами 0, 1 и 3. Проверьте одинаковые условия в каталоге,
подтверждении и сохранённом заказе. После создания заказа измените тариф: старый
платёж должен выдать прежний лимит. Снизьте лимит подписки с двумя работающими
профилями до 1: оба ключа работают, третий не создаётся. После увеличения до 3
создание снова доступно. Проверьте, что изменение не применяется до успешной выдачи
всех профилей и не подменяется текущим тарифом при повторе после сбоя. Принятая до
снижения pending-выдача не отменяется. Проверьте возврат к основному профилю при 0.


## Перевыпуск — v0.015

Для каждого поддержанного контракта API и WG проверьте отдельный профиль на устройстве.
Начните перевыпуск: старые настройки не скачиваются, новый ключ не создаётся до
подтверждённого API отключения старого. Убедитесь в фактическом отзыве старого доступа,
импортируйте новый файл/ссылку и проверьте интернет; остальные профили должны работать.
Имитируйте потерю ответа отключения и создания, перезапустите worker: второй новый ключ
не появляется. Во время незавершённой выдачи отзовите профиль и проверьте отсутствие
доступа по обеим возможным конфигурациям. Проверьте окончание срока, продление во время
операции и повторный перевыпуск уже заменённого ключа. Для WG проверьте наличие свободных
адресов. Стендовая проверка пока не выполнена; автоматические тесты используют подмены.


## Основной профиль — v0.016

Для Legacy, Clients JSON и WG начните перевыпуск основного профиля при работающем
дополнительном. Проверьте перерыв только у основного, фактическое отключение старого

потерю ответа отзыва/выдачи и перезапуск. Проверьте окончание срока в промежуточном
состоянии: обе возможные идентичности должны быть отключены; после оплаты прежний
ключ не возвращается. При отказе очистки продление должно ждать подтверждения.
Эти стендовые сценарии пока не выполнялись; автоматические тесты используют подмены API.


## Ссылка подписки — v0.017

Перед тестом включите актуальные шаблоны прокси. На тестовой VLESS-подписке импортируйте
URL как подписку в каждом целевом клиенте, проверьте декодирование и реальный трафик.
Замените URL и убедитесь в 404 по старому; отключите — экспорт закрыт, ранее импортированный
ключ всё ещё работает до отдельного перевыпуска. По умолчанию основной перевыпуск
отключает URL; при явном согласии сохранённая ссылка после завершения отдаёт новый ключ.
Проверьте обновление в клиенте и его фактический интервал. При истечении срока экспорт
недоступен, после оплаты восстанавливается для включённого URL. Проверьте общую NAT-сеть
с rate limit. Имитируйте отказ upstream и TLS; приватный токен не должен попасть в
access/error/runtime логи, CDN или APM. Очищайте отчёт от токенов. Эти реальные сценарии
ещё не выполнялись; unit-тесты проверяют API и сформированные шаблоны.


## Пробный доступ — v0.018

На стенде настройте реальный Telegram-вход и условия, затем включите trial с бюджетом
2 и сроком 1 день. У нового Telegram-аккаунта проверьте выбор протокола, принятие условий,

бюджет ожидающих заявок и двойное нажатие. Выключите политику после принятия: выдача
должна продолжиться по сохранённым условиям. При сбое повтор использует тот же ключ;
срок не прибавляется заново. Купите тариф во время pending trial и после выдачи:
ключ/оставшиеся дни сохраняются, оплаченные ограничения не заменяются поздним trial.
Проверьте отсутствие доппрофилей, перевыпуска и URL до покупки и доступность после неё.
Эти реальные сценарии ещё не выполнялись; автоматические тесты используют подмены.

### Реферальные бонусы v0.020

- Программа изначально выключена. Задайте бонус, обе минимальные суммы и малый лимит;
  проверьте версию/аудит, отключение и остаток мест. Самоприглашение не проходит.
- Платный клиент получает ссылку; новый аккаунт принимает её до первого заказа/trial.
  Без явного принятия переход по ссылке ничего не привязывает. Другой код не заменяет
  принятый; аккаунт с прежними заказами отклоняется. Проверьте /shop и Telegram-вход.
- Сохранённые условия переживают отключение/редактирование программы. Неоплатившие
  приглашения занимают лимит. Два одновременных принятия последнего места дают одно принятие.
- Подтвердите подходящий платёж каждым используемым способом: ручной, тестовый YooKassa,
  тестовый Stars. Повтор события и вторая покупка не начисляют повторно. Неподтверждённый,
  отменённый, trial и покупка ниже порога после промокода не дают бонус.
- Потратьте часть дней на платную подписку. Повторите UUID, вызовите ошибку панели и
  перезапустите worker: сумма списывается один раз, срок не удваивается; дополнительные
  устройства продлеваются, текущий лимит сохраняется. Платные и бонусные продления
  одного протокола не обходят ошибку предыдущего заказа.
- Проверьте отсутствие email/Telegram ID друзей в кабинете, очистку при выходе и поздних
  ответах. При возврате платежа бонус автоматически не сторнируется: до запуска нужна
  согласованная процедура поддержки; денежного вывода и админского изменения баланса нет.


### Резервные копии v0.021

- Создайте снимок базы при работающем магазине и наличии записей в WAL. Проверьте
  скачанный с внешнего хранилища архив тем же релизом инструмента.
- Проверьте неправильный пароль, изменённый байт архива и другой ENCRYPTION_KEY:
  ошибка не создаёт результат/каталог и не раскрывает секреты в JSON/stderr.
- Восстановите на отдельном стенде. Каталог 0700, файлы 0600; рабочие данные не меняются,
  старые sessions/tickets отсутствуют. Повтор с существующим каталогом отклоняется.
- Сверьте тарифы, серверные профили, очереди, устройства, сроки, купоны и реферальный
  баланс. Расшифровка проходит; VPN и платёжные состояния проверяются отдельно.
- Для Docker создайте и проверьте копию по BACKUP.md, убедитесь в доступе uid 10001
  к новому volume. На этапе проверки BACKGROUND_TASKS=false, второго polling-бота нет.
- Имитируйте аварию после снимка и оформите процедуру сверки более новых внешних оплат,
  состояний узлов и очередей. Сам по себе verify не подтверждает эту процедуру.

### Локальная диагностика v0.023

- Без ADMIN_TOKEN endpoint запрещён; с токеном ответ no-store и без email/Telegram ID,
  ключей, доменов, идентификаторов заказов и текстов ошибок провайдера.
- Создайте ожидающее продление, повтор после ошибки, смену ключей и просроченный отзыв.
  Сверьте счётчики/возраст и отсутствие двойного счёта устройства в очередях ротации.
- Перезапустите приложение: прошлый успешный цикл worker не должен сохраниться. После
  нового цикла метка обновляется. Имитируйте ошибку/длительное выполнение/остановку
  фоновых задач и проверьте предупреждения, не потеряв сами задания.
- Заполните вместимость сервера, переведите его в draining, устарьте checked_at.
  Отчёт не должен запускать сетевой probe или объявлять реальный трафик исправным.
- Проверьте выход во время запроса и два запроса в разном порядке: старые ответы не
  восстанавливают данные. JSON в админке очищается, HTML-значения экранируются.
- В реальном Docker выполните status.py на настроенном loopback-порте: 0/1/2 по
  результату, без proxy/перехода по redirect и утечки токена в stdout/stderr. Проверка
  только локального endpoint не заменяет покупку/чек, VPN и восстановление копии.

- Создайте настоящий managed v0.022 через старый переход. Убедитесь, что его база в

  контроллер должен выбрать именно действующий внешний volume и сохранить эти данные.
- До остановки проверьте отказ на изменённом mount/Compose/marker, пропавших исходниках,
  симлинках и конфликтующей истории. Старый незавершённый переход нельзя перезаписать.
- Проверьте принятие committed-журнала старого v0.022 без activation.json: plan ничего
  не создаёт, prepare сохраняет подтверждение до замены журнала и архивирует прежний.
- Имитируйте отказ сборки, копии, миграции и старта для managed-установки. Возврат должен
  идти в предыдущий текущий том с DATA_DIR=/app/data/restored. Повторите prepare/rollback
  дважды, затем activate: прежняя история не теряется и база не берётся из старого тома.
- Подтвердите сохранность платных/бонусных заказов, устройств, ссылок и балансов реальными
  проверками, единственный worker/бот, отказ отката после активации и независимую копию.


### Автоматический Docker-стенд v0.025

Сначала проверьте job docker-staging по DOCKER_STAGING.md. Его зелёный результат
покрывает Docker lifecycle и сохранность синтетических данных, но не реальную выдачу,
платёж/чек, бота, ACME и нагрузку VPS. При красном/пропущенном job не переносите
результаты локальных pytest как подтверждение Docker-перехода.


### Автоматическая приёмка WireGuard v0.027

Отдельный обязательный job `wireguard-staging` проверяет реальную выдачу через
магазин/агент, kernel handshake, IPv4 NAT до контролируемого приёмника, продление и
автоматический отзыв по сроку. Состав и точные границы — [WIREGUARD_STAGING.md](WIREGUARD_STAGING.md).
Публичный интернет, IPv6/DNS, VLESS, платёжный провайдер и чистый VPS этим job не
подтверждаются. Их приёмка по настоящим устройствам/инфраструктуре остаётся открытой.


### Подтверждение Legacy-записи v0.028

На отдельной панели проверьте add/renew/disable с чтением inbound после записи.
При перехваченном/проигнорированном изменении и ответе success оплаченный заказ не
должен становиться active; конфиг остаётся недоступным. После исправления состояния
повтор выдаёт тот же UUID и первоначальный срок. При неподтверждённом disable задача
остаётся на повтор, а не объявляется отключённой. Проверьте реальным клиентом, что
после подтверждённого отзыва новый трафик не проходит: одно чтение панели этого не
доказывает. Отдельно проверьте потерю ответа после удалённой записи, дубли UUID,
коллизии email/subId и сохранение пользовательских полей при продлении.


### Предварительная проверка панели v0.030

Перед созданием тестовых заказов запустите [panel_check.py](PANEL_CHECK.md) для
отдельного стенда. Требуется api_checks_ok с явно подтверждённым inbound ID.
Это проверка входа/чтения схемы, а не готовности полного подключения. После неё
по-прежнему необходимы покупка, настоящий трафик, продление, смена ключа и отзыв
на реальной панели. Приватный профиль/пароли не прикладывайте к отчёту.


### API Remnawave и URL-подписка — v0.043

Этот прогон выполняется только на отдельном стенде с тестовым VLESS-профилем и
тестовой учётной записью. Не используйте production-панель и не проводите реальную
оплату. Для магазина выберите API-режим Remnawave, отдельный тестовый сервер и
ограниченную тестовую группу; токен и URL подписки не копируйте в журнал или отчёт.

1. До заказов запустите read-only диагностику из работающего контейнера магазина:
   `docker exec "$SHOP_CONTAINER" python scripts/panel_check.py --server "$SERVER_ID"`.
   Ожидайте `status=api_checks_ok`, `authentication=true`,
   `supported_schema=true`, `user_api=true`; для Remnawave проверки inbound и
   inbound ID помечаются как неприменимые. Отчёт не должен содержать токен, URL
   подписки, UUID, email или идентификатор панели. Ошибка проверки блокирует создание
   тестового заказа. Диагностика читает API и не проверяет права записи.
2. Создайте заказ с тестовым тарифом и завершите его только штатным ручным
   подтверждением тестового платежа. До подтверждения профиль не выдаётся. После
   подтверждения в тестовой панели должна появиться ровно одна запись: имя
   `p` + UUID профиля без дефисов в нижнем регистре, тот же VLESS UUID,
   статус ACTIVE и срок, совпадающий с заказом. Зафиксируйте результат без секретов.
3. Убедитесь, что панель выдала HTTPS subscription URL, а кабинет магазина предлагает
   импортировать именно подписку. Добавьте её в выбранный тестовый VPN-клиент и
   проверьте обновление профиля и реальный туннельный трафик. Не публикуйте ссылку:
   она содержит секрет доступа.
4. Имитируйте потерю ответа после создания пользователя, затем повторите обработку
   того же тестового заказа. Дубликат пользователя, второй UUID и повторное начисление
   срока недопустимы. После восстановления связи запись должна повторно прочитаться и
   совпасть с исходной идентичностью.
5. Продлите существующий тестовый профиль. Имя, UUID и подписка должны сохраниться,
   срок должен увеличиться ровно на оплаченный тестовый период. Имитируйте потерю
   ответа после записи продления и проверьте безопасный повтор.
6. Отзовите тестовый профиль. Проверьте статус/ссылку панели и, отдельно, прекращение
   VPN-трафика на тестовом устройстве. Один только HTTP-ответ или скрытие ссылки не
   доказывает отзыв доступа.
7. Восстановите тестовую группу и повторите read-only диагностику. Сохраните дату,
   версию панели, версию магазина, идентификатор тестового заказа и очищенные
   результаты каждого шага. Любой непроверенный шаг остаётся открытым блокером.

`api_checks_ok` подтверждает доступ к чтению API и схему ответа; он не доказывает
покупку, права записи, выдачу subscription URL, совместимость конкретного клиента,
VPN-трафик или отзыв доступа. Этот сценарий пока не выполнен на реальной панели.
