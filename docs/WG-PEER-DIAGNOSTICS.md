# Shop v0.060: диагностика и восстановление WireGuard-пира по пользователю

## Назначение
Проверить, **почему пользователь не получил peer в WGDashboard**, не раскрывая API-ключи, WireGuard private key, конфигурации и пользовательские ссылки. Не путать сетевой WireGuard-туннель с административным API панели.

Действующий сервер на 25 ноября 2026 года — `193.238.155.39`, панель
`https://wg.pushok.shop`. На интерфейсе `wg0` WireGuard слушает UDP-порт
`51820`. Адрес в клиентском профиле — `wg.pushok.shop:51820`.

## Семидневное гостевое подключение

Shop запоминает конфигурацию `wg-guest` при создании гостевой подписки из магазина или Flow. Подключение использует существующие реквизиты WGDashboard. Если в Shop есть отдельная подходящая запись панели с конфигурацией `wg-guest`, гостевая выдача предпочитает её. На узле Pushok для этой конфигурации задан UDP-порт `65353`. Клиент получает адрес и порт из экспорта панели. Срок окончания и отзыв пира относятся к этой же конфигурации.

Если `wg-guest` выключена или отсутствует на выбранной панели, запрос остаётся в очереди. В карточке пользователя можно проверить закреплённый пир. Подписки, для которых предыдущая версия уже создавала ключ, обслуживаются по прежней привязке.

## Админка
`Пользователи → карточка пользователя → WireGuard → Проверить пир`.

Доступно только роли **Разработчик**. Backend читает локальную подписку и сохранённый ключ `wgdashboard_keys`, затем в режиме **только чтения** проверяет интерфейс и ищет публичный ключ Shop на **закреплённом сервере**. Он не создаёт, не удаляет и не переносит peer, не генерирует ключ и не изменяет подписку.

Результат:
- `no_subscription` — нет WG-подписки;
- `server_unbound` / `server_missing` — подписка не закреплена за правильным узлом;
- `other_backend` — исходный профиль привязан к Pushok WG-агенту, а не WGDashboard. Смена адреса новой панели **не переносит** такой профиль;
- `key_not_created` / `key_unreadable` — Shop не сохранил ключ или не может его прочитать;
- `peer_missing` — в закреплённой панели отсутствует peer с публичным ключом Shop;
- `peer_found` — peer существует; это **не доказывает handshake или интернет**;
- `peer_restricted` — peer существует, но ограничен в WGDashboard;
- `panel_auth_failed` — отказ в авторизации API 401/403;
- `panel_api_missing` — API недоступен по сохранённому пути 404/405;
- `panel_connection_failed` / `panel_timeout` / `panel_unavailable` — проблема соединения или ответа сервера.

В статусе также показываются безопасные: название закреплённого сервера, состояние локальной подписки, наличие готовой конфигурации, число повторных попыток по очереди. Не показываются ни URL панели, ни токены, ни public/private key.

### Повторить выдачу
Появляется **только у ожидающей автовыдачи**, когда владелец разрешил эту политику, подписка ещё `pending`, исходный сервер активен, доступен WGDashboard с `schedule_expiry` и `panel_timezone`, срок заявки не истёк. Кнопка лишь ставит прежний `flow_auto_grants` в очередь на повтор. Она сохраняет `subscription_id`, `server_id` и идентичность пира — не создаёт новую подписку по клику.

Если подписка была на старом сервере, **автоматический перенос отключён**: необходимо сначала выполнить отдельный подтверждённый перенос/перевыпуск с правильным отзывом старых ключей и сохранением истории платежей.

### Восстановить отсутствующий пир

После статуса `peer_missing` у **действующей** подписки появляется отдельная кнопка «Восстановить отсутствующий пир». При `peer_found` разработчик может нажать «Обновить конфигурацию»: Shop прочитает `.conf` из панели, проверит прежний ключ и обновит зашифрованный профиль без создания нового пира. Действие требует подтверждения разработчика и допустимо только если:

- исходный `server_id` всё ещё привязан к поддерживаемому WGDashboard и узел доступен;
- в `wgdashboard_keys` сохранился прежний шифрованный ключ;
- нет незавершённых заказов и смены ключа;
- срок подписки ещё не истёк и профиль не отозван.

Shop **повторно использует прежний ключ**, проверяет отсутствие пира, создаёт его на том же узле через штатный WGDashboard-адаптер, проверяет результат, загружает новый `.conf` и обновляет шифрованную конфигурацию подписки. Срок, идентичность пользователя, способ оплаты и `server_id` не изменяются. Если пир уже есть, возвращается `already_present` без лишней записи.

При ошибке панели или неподтверждённой конфигурации Shop оставляет прежнюю локальную запись и ключ для повторной попытки. Если исходный сервер больше недоступен, **не переключает профиль на другой сервер** и возвращает ошибку — для этого нужна отдельная ручная миграция, чтобы не потерять права доступа или ключи.

## API
- `GET /shop/api/admin/users/{user_id}/wireguard/peer` — developer-only, read-only (без токенов и URL).
- `POST /shop/api/admin/users/{user_id}/wireguard/retry` — developer-only, только возврат существующей, ещё действующей `pending`-заявки в очередь. Нет сетевых side effects.
- `POST /shop/api/admin/users/{user_id}/wireguard/restore` — developer-only, явное восстановление отсутствующего пира на ранее закреплённом сервере без изменения ключа, срока или прав.

Оба защищены штатной авторизацией, аудитом и rate limit Shop. Приватные ответы не кэшируются.
