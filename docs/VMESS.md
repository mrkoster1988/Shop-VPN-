# VMess AEAD через 3x-ui

В текущем `main` магазин создаёт, продлевает и отключает VMess-клиентов через
**Clients JSON API 3x-ui**. Покупателю доступны ссылка `vmess://`, QR-код и скачивание
текстового файла, отдельные устройства и перевыпуск ключа. Тарифы, trial и промокоды
используют общий сценарий магазина с протоколом `vmess`.

Это реализация и контрактные тесты, а не подтверждение работы на вашем VPS.
Закреплённый установщик v0.054 ещё не содержит этот этап из `main`.

## Поддерживаемый вариант

| Параметр | Условие |
|---|---|
| Панель | 3x-ui с Clients JSON API и Bearer-токеном |
| Протокол inbound | `vmess`, включён |
| Аутентификация | AEAD, `alterId=0`; шифрование клиента `security=auto` |
| Транспорт | TCP без HTTP-заголовка либо WebSocket без early data |
| Защита | TLS на самом inbound, доверенный сертификат и правильное SNI |
| Профиль покупателя | JSON v2, закодированный в base64 после `vmess://` |
| Обновляемый URL подписки магазина | Пока доступен только для VLESS |

Legacy API, Remnawave для VMess, gRPC/XHTTP, REALITY и отключённый TLS не входят
в этот этап. Завершение TLS на внешнем прокси при `security=none` у inbound не
поддерживается. Расширенные настройки TLS, клиентские сертификаты и произвольные
транспортные опции не экспортируются. Используйте обычный TCP/WS + TLS и проверьте
импорт в выбранной версии клиентского приложения.

## Настройка владельцем

1. Создайте отдельный включённый VMess inbound в 3x-ui. Выберите TCP (без маскировки
   HTTP) или WebSocket, включите TLS и установите действующий сертификат.
   Сначала проверьте ручное подключение к нему.
2. Включите API и получите Bearer-токен панели. При включённой 2FA используйте
   токеновый API; магазин не вводит одноразовый код и не выключает 2FA.
3. Откройте в магазине «Серверы» → добавление → **VMess AEAD**.
4. Укажите HTTPS-адрес панели с секретным подпутём, например
   `https://panel.example/private`, без `/panel/api` и без пути магазина `/shop`.
5. Заполните API-токен, ID inbound, адрес подключения, внешний порт и SNI.
   Адрес подключения — DNS-имя или IP VPN-узла, а не URL панели. Порт может
   отличаться от внутреннего при пробросе; доступность порта проверяется клиентом.
6. Выберите TCP либо WS. Для WS укажите точный путь, например `/vpn`, и Host,
   если он задан в inbound. Путь должен начинаться с `/`, без query/fragment,
   пробелов и early data. Для TCP путь и Host не нужны.
7. Сохраните сервер: он создаётся **выключенным**. Выполните «Проверить API»,
   затем переведите сервер в активное состояние. Только после этого он участвует
   в назначении новых подписок, если не исчерпана его вместимость.

API-проверка подтверждает доступ к Clients JSON и соответствие настроек inbound.
Она не проверяет внешний порт VPN, сертификат VPN-узла, DNS и реальный трафик.
Если при сохранении изменён токен или endpoint, нужна новая проверка перед активацией.
Когда у сервера уже есть подписки, его endpoint/транспорт нельзя подменить:
для другого подключения создайте отдельный сервер.

Пример поля `settings` для создания сервера через API магазина (токен — заглушка):

```json
{
  "api": "clients",
  "url": "https://panel.example/private",
  "token": "REPLACE_WITH_YOUR_3XUI_API_TOKEN_32_CHARS_MINIMUM",
  "inbound_id": 7,
  "address": "vpn.example",
  "port": 443,
  "network": "ws",
  "sni": "vpn.example",
  "ws_host": "vpn.example",
  "path": "/vpn"
}
```

Для TCP замените `network` на `tcp`, а `ws_host` и `path` на пустые строки.
Профиль хранится зашифрованным; токен панели не попадает в ссылку или публичную
карточку сервера. Ссылка покупателя содержит его UUID и сама является секретом.

## Что происходит при записи

Магазин ищет клиента по стабильному `pushok_<UUID>`. Для создания отправляет
`POST /panel/api/clients/add` с объектом `client` и одним `inboundIds`.
Для продления и отключения использует `POST /panel/api/clients/update/:email`.
Существующие лимиты и дополнительные поля клиента сохраняются.

После записи магазин повторно читает клиента и проверяет UUID, email, subId,
единственную привязку к нужному inbound, точный срок и `enable`. Для выдачи также
проверяются `security=auto`, отсутствие старого alterId и соответствие транспорта.
Успешного HTTP-ответа без совпадения состояния недостаточно для выдачи ссылки.
Если ответ потерян, повтор использует тот же UUID и не создаёт новый доступ.

Отзыв устанавливает `enable=false` и проверяет результат. Изменившиеся настройки
TLS/транспорта или шифрования не мешают отключить ранее созданный UUID.
Неизвестная идентичность клиента или привязка к нескольким inbound остаются ошибкой:
магазин не меняет чужой или совместно используемый доступ.

## Приёмка на реальном сервере

1. Зафиксировать версию/коммит 3x-ui, версию клиента, ОС, TCP/WS и настройки TLS.
2. Проверить автоматическое время на VPS и устройстве; импортировать полученную
   `vmess://` целиком через ссылку, файл или QR. Не отключать проверку сертификата.
3. Подтвердить реальное подключение и передачу трафика через узел.
4. Продлить подписку: UUID прежний, срок увеличен, второй клиент не появился.
5. Проверить дополнительное устройство и перевыпуск: UUID разные, старый ключ
   перестаёт работать после завершения отзыва.
6. Проверить trial и покупку, затем истечение срока и повтор после временного
   отказа API. Подтвердить прекращение доступа на клиенте и в панели.
7. Повторить для TCP и WS; сохранить результат каждого сочетания отдельно.

Локальные тесты подменяют API панели. Они покрывают создание, повторы после потери
ответа, нарушения идентичности, несовпадение транспорта, неподтверждённую запись,
продление, устройства, перевыпуск и отзыв. Реальная приёмка VMess пока открыта.
